# Tool catalogue (v1 contract)

Conventions: names are `shell_<verb>_<noun>`. Every tool takes `target: string` (optional when exactly one target exists or `SHELL_MCP_DEFAULT_TARGET` is set). **Gate op** is the operation in `docs/ARCHITECTURE.md` §4.3; the gate enforces the policy for it independently of this table.

Annotations: `read` → `readOnlyHint: true, destructiveHint: false, idempotentHint: true, openWorldHint: true`. `operator` → `readOnlyHint: false, destructiveHint: false, openWorldHint: true` (`idempotentHint` per tool). `destructive` → `readOnlyHint: false, destructiveHint: true, idempotentHint: false, openWorldHint: true`. Every tool sets `title` and an `outputSchema`.

Common optional inputs on tools that run a process: `timeout_seconds` (1..`SHELL_MCP_MAX_TIMEOUT`, default `SHELL_MCP_DEFAULT_TIMEOUT`), `max_output_bytes` (1..`SHELL_MCP_MAX_OUTPUT_BYTES`).

**Profiles.** `read-only` registers the read tier; `operator` adds the operator tier; `admin` adds the destructive and privileged tiers — `admin` is the profile for a fully capable deployment. Each host's gate and privileged policies still decide what actually runs.

**Tier ceiling.** Every gate request a tool makes carries the tool's registered tier (the tier of its section below) as the request's `ceiling` (ARCHITECTURE §4.1). The gate, and the helper for `shell_priv_*` tools, refuse any operation or command above min(their policy's `max_tier`, `ceiling`) with `tier_denied`, in one check before anything runs. So a tool can never act above its own tier on a host, even through a server mistake or a policy edited between two requests, and a profile's tools are bounded on the host as well as by registration. The one exception lowers it: `shell_run_command`'s `exec` carries the tier of the command its preview resolved when the call was approved, and otherwise the highest tier that needs no approval (Destructive tier below). The ceiling does not defend against a compromised server, which can send any ceiling; the host policies are the boundary for that.

**Approval (D-006).** Destructive tools, privileged tools of tier operator or above, and any tier listed in `SHELL_MCP_APPROVAL_TIERS` are approval-gated. How approval is collected is `SHELL_MCP_APPROVAL_METHOD`:
- **`web` (out-of-band).** The first call computes a preview and returns `approval_pending` (`ok: false`, nothing ran) with an `approval` object `{id, status, url, expires_at, summary}`. Its message tells the model to show the user the URL exactly as written. The approver opens the approval page from a bookmark (entering the id) or from the server's own optional push, never from a link in the chat; checks the origin banner, the server's description, the arguments and the preview; and approves or declines with a current TOTP code from their authenticator. The approval page can be opened on any device; only the code must come from the approver's authenticator. The model then calls the tool again with the same arguments plus `approval_id`, and the server runs exactly that operation, once.
- **`confirm-argument`.** The same record and binding, but the re-call carries `approval_id` and `confirm: true`, and the server records the approver as `model (confirm-argument)`, with a WARN at startup and on every use. **This turns approval off against a prompt-injected model**: the model chooses the argument.
- **`none` (the default).** Approval-gated tools refuse with `approval_unavailable` and send nothing.

**Approval codes.** `approval_pending`: approval is required or still awaited (a re-call while the record is pending waits up to 20 s, then answers this again). `approval_declined`: the approver declined. `approval_invalid`: the id is unknown, expired, already used, or does not match the call (principal, tool, target, arguments), or the target or its policy changed since approval (the fresh preview's or policy's hash differs; for a privileged tool, the gate policy's or the privileged policy's); request a new approval. `approval_unavailable`: the method is `none`, or too many approvals are pending for this principal (5), or the store is full.

**Approval inputs and metadata.** Every tool that can be approval-gated (operator and destructive tiers) has an optional `approval_id` input (26 characters, `^[a-z2-7]{26}$`), whatever the configuration, so the catalogue does not depend on it; on a call that needs no approval, giving one is a `validation_error`. Under `confirm-argument`, and only then, those tools also have a `confirm` input. Approval-gated tools carry `_meta["anthropic/requiresUserInteraction"]: true`, so Claude Code shows their permission prompt on every call, without "always allow". That is client-side defence in depth, not approval: the server cannot verify it.

**Read tier: what the table leaves open (S3).**
- **Results.** `structuredContent` is the envelope. The text block is one summary line (`ok: <counts and flags>` or `error: <code>`), which never carries a string from the host or the caller, followed by the same envelope JSON, so a client that passes only text to the model still sees the data. Host content (files, logs, diffs, command output, process lines, names) is data in envelope fields, never phrased as instructions.
- **Common inputs.** `timeout_seconds` is accepted by the tools that start a process on the target: `shell_get_service_status`, `shell_list_services`, `shell_get_journal`, `shell_get_git_status`, `shell_get_git_log`, `shell_get_git_diff` and `shell_run_read_command`. `max_output_bytes` is accepted by the tools that return free text: `shell_get_journal`, `shell_get_git_diff` and `shell_run_read_command`. Other tools use the server default timeout.
- **Bounds.** Schema maxima are static, so the catalogue is the same for every deployment. Where a bound depends on a setting, the schema gives the highest value that setting can take: `timeout_seconds` ≤ 3600, `max_output_bytes` and `max_bytes` ≤ 4194304, `lines` ≤ 10000, `max_depth` ≤ 32, find `limit` ≤ 10000. The configured value then applies: `SHELL_MCP_MAX_TIMEOUT` and `SHELL_MCP_MAX_OUTPUT_BYTES` are checked by the server (`validation_error`), and policy limits are checked by the gate (`bad_request`). An optional integer that is given must be in range: `0` is refused, never read as "default". An omitted one takes the default in the table.
- **Input forms.** Paths (`path`, `root`, `repo`, `cwd`) must be absolute and already clean; they are refused, never cleaned. `unit` is an exact name with a type suffix. `since`/`until` are as in the table, and `since` may not be after `until`. `modified_within` is `N` followed by `s`, `m`, `h`, `d` or `w` (`30m`, `2d`), at most ten years. `user` is a user name or a numeric uid. Filters (`name_contains`, `name_glob`) are at most 256 bytes; `name_glob` has no `/`. `offset` and `tail_lines` may not both be given. `args` holds at most 64 items, each at most 1024 bytes, with no NUL, CR or LF. `command_id` matches the policy's id pattern.
- **Output bounds and redaction order.** The gate caps and redacts first, with its built-in rules and the policy's patterns. The server then redacts every string in the data and every warning with its built-in rules and `SHELL_MCP_REDACT_PATTERNS`. It cuts each free-text field (journal output, diff, file content, stdout, stderr) to `max_output_bytes` (default `SHELL_MCP_MAX_OUTPUT_BYTES`), redacting before the cut and again after it, and never inside a UTF-8 sequence. Last, it drops trailing entries of a list (mounts, processes, units, directory and find entries, git status entries, commits, certificates) until the data fits `SHELL_MCP_MAX_OUTPUT_BYTES`. Every cut sets the tool's `truncated` flag (for commands, `stdout_truncated`/`stderr_truncated` in `data` and in `exec`).
- **`shell_run_read_command`.** It sends one `exec` request at ceiling `read`. The gate refuses a `command_id` that is not declared (`policy_denied`) and a command whose tier is above `read` (`tier_denied`, its message naming the ceiling) in the same check that applies its `max_tier`, before anything is executed; it then matches the templates. The tool does not read the policy first, so there is no window between a tier check and the run. A non-zero exit is `ok: true` with `exec.exit_code`.
- **Audit arguments.** The audit arguments are `target`, plus `path`, `recursive`, `root`, `repo`, `unit`, `command_id`, `cwd`, and `args_count` (the number of `args`, never their values). Filters, times and content are never logged.

**Operator tier: what the table leaves open (S4a).** The read tier's rules on results, input forms, static schema maxima and the redaction order apply here too.
- **One request, ceiling `operator`.** Each tool validates its input, sends one gate request of its op at ceiling `operator` and shapes the result. The gate re-validates everything against its policy: write roots, the deny list, the protected set (`.git` included), modes, units and verbs, repositories and remotes, command tiers and templates. `shell_run_command` is registered at `operator` in the operator profile, where it runs commands of tier `read` or `operator` only (the gate refuses a `destructive` command with `tier_denied` naming the ceiling), and at `destructive` in the admin profile (Destructive tier below).
- **`idempotentHint`.** True when repeating the call with the same arguments changes nothing more on the host: `shell_write_file` (the same content again; with `expected_sha256` a repeat is refused), `shell_make_directory` (a repeat is `exists`), `shell_copy_path` (a repeat is `exists`, or the same copy with `overwrite`) and `shell_set_permissions`. False for `shell_control_service` (every call acts on the unit again), `shell_git_pull` (a later call can fetch new commits), `shell_run_command` (any declared command) and `shell_move_path` (a repeat finds the source gone; it is not safe to retry blindly, since a source recreated in between would be moved again).
- **Write results.** `shell_write_file` returns `path`, `created`, `bytes`, `mode`, `old_sha256` (empty for a new file), `new_sha256`, `lines_old`, `lines_new`, `lines_delta` and `owner_preserved`; `shell_copy_path` returns `source`, `destination`, `created`, `bytes`, `mode`, `sha256` and `old_sha256`. Neither returns content. Both set the envelope's `verified: true`, which means the gate re-opened the file, re-read it and its SHA-256 equalled what was written. The gate answers a mismatch with `verify_failed`; a success whose `verified` is false is turned into `verify_failed` too, never a success with a warning. `expected_sha256` (64 lowercase hex digits) is passed through: the gate refuses the write with `exists` when the file's current content has another hash, or when the file is replaced or rewritten between that check and the commit (a verified replace, POLICY §3), and with `not_found` when the file does not exist. A filesystem without `RENAME_EXCHANGE` (for example NFS) refuses a write with `expected_sha256`, and an approved copy or move over a file, with `bad_request`; `shell-mcp-gate check-policy` warns about such a write root. A write without `expected_sha256`, and an unapproved copy or move with `overwrite`, replace whatever regular file is there at the commit (POLICY §3, unconditional replaces).
- **Inputs.** `content` is required (an empty string writes an empty file) and, like `stdin`, is UTF-8 text of at most 1048576 bytes, checked by the server before anything is sent (the policy's `max_write_bytes` and `max_stdin_bytes` then apply on the gate). Modes are 3 or 4 octal digits; which bits are allowed (no setuid, setgid, sticky or world-write) is the gate's rule, so those modes reach the gate and are refused there with `policy_denied`. `action` is `start`, `stop`, `restart` or `reload`. `create` defaults to true; `parents` and `overwrite` to false. `timeout_seconds` is accepted by the tools that start a process on the target (`shell_control_service`, `shell_git_pull`, `shell_run_command`) and `max_output_bytes` by `shell_run_command`; the file tools use the server's default timeout.
- **Errors.** Gate refusals pass through with their code and message: `path_denied` (outside the write roots, deny list, protected set), `policy_denied` (unit, verb, repository, remote, dirty tree, non-fast-forward, mode bits), `not_authorized` (polkit), `exists`, `not_found`, `exec_failed`, `tier_denied`, `template_mismatch`.
- **Approval.** With the default `SHELL_MCP_APPROVAL_TIERS` (`destructive`) the operator tools run without approval, and giving them an `approval_id` is a `validation_error`. When the tiers list `operator`, every operator tool is approval-gated (section "Approval" above): with `SHELL_MCP_APPROVAL_METHOD=none` it refuses every call with `approval_unavailable`, whatever its arguments, and sends nothing to the target; otherwise the first call returns `approval_pending` after the preview below, and the re-call with `approval_id` runs the operation once. `shell_run_command` is the exception: its gating follows the command's tier (a `read` command never needs approval, an `operator` one only when the tiers list `operator`), decided after its `exec_preview`; under `none` a command that needs approval is refused after that preview, and nothing runs.
- **Audit arguments.** `target`, plus `unit` and `action`; `path`, `mode`, `create`, `parents` and `content_bytes` (the size, never the content); `source`, `destination` and `overwrite`; `repo`; `command_id`, `args_count`, `cwd` and `stdin_bytes` (never argument values or stdin). `expected_sha256` is not logged. A gated call's line also carries `approval_id` and `approval_outcome` (`pending`, `used`, `invalid` or `declined`). The gate's and the helper's own audit lines record each request's `ceiling`.

**Approval previews (S4b-1b).** An approval-gated call's first request computes a preview from the gate's existing read operations, at the tool's ceiling; nothing that changes the host is sent. The preview, its SHA-256 and the gate's policy SHA-256 (from the preview responses' `gate` block; for a privileged tool, the SHA-256 of the gate's and the privileged policy's hashes, privileged tier below) are bound to the approval record, and the re-call computes the preview again: a different hash is `approval_invalid` ("the target or policy changed since approval"). Previews hold only what does not change by itself between request and re-call: no memory figures, unit state timestamps or durations. A gate refusal while computing a preview (for example `path_denied`, or a file whose first bytes are a private key, which `read_file` refuses) is the call's result, and no approval is requested. The record's description is one line the server writes from the tool and the canonical arguments (for example "Write 12 bytes to /srv/app/config.yaml on app-host"). A path, unit or name appears in it only when it is plain (letters, digits and `._/@+=,:~-`, no spaces); otherwise the description says that it is shown in the arguments, where it is escaped data in a table. **Destructive tier: what the table leaves open (S4b-2a).** The read tier's rules on results, input forms, static schema maxima and the redaction order apply here too.
- **Registration and approval.** Destructive tools are registered only in the `admin` profile, with `readOnlyHint: false`, `destructiveHint: true`, `idempotentHint: false`, `openWorldHint: true`. They are approval-gated under every configuration, so they carry `_meta["anthropic/requiresUserInteraction"]: true` in every catalogue variant; under `SHELL_MCP_APPROVAL_METHOD=none` every call is `approval_unavailable` and nothing is sent to the target.
- **`shell_delete_path`.** The first call sends one `delete_preview` at ceiling `destructive` and returns `approval_pending`. The re-call sends `delete_preview` again (its hash must equal the approved preview's, else `approval_invalid` and nothing is deleted), then `delete` with `expected_preview_sha256` set to that fresh preview's `preview_sha256`, taken from the gate's answer before the server's redaction. `expected_preview_sha256` is not a tool input. The result is `path`, `type`, `entries`, `bytes` and `deleted: true`; a gate answer without `deleted` is `internal`, never a success.
- **Errors.** `exists`: the tree changed after the fresh preview, either before anything was deleted ("nothing was deleted") or during the deletion ("N of M entries were deleted and K were not"; preview the path again to see what remains). Nothing that was not in the preview is deleted in either case. When an entry that was set aside could not be put back (its name was taken again), the message also names the temporary path it was left under (`.shell-mcp-delete-<32 hex>`) and the path it came from; it is not deleted, and the gate refuses every path that is or holds such a name until an operator recovers it (POLICY §3). `path_denied` (a root, outside the write roots, the deny list, the protected set and `.git`, a final symlink, a mount point, a device node, a set-aside name), `bad_request` (a non-empty directory without `recursive`, or a filesystem without `RENAME_NOREPLACE`), `too_large` (`max_delete_entries`) and `not_found` pass through from the preview or the delete.
- **Filesystems.** Deletes need `RENAME_NOREPLACE` and are refused, with nothing deleted, on a filesystem without it: for example NFS, and FUSE filesystems whose server does not implement rename2. SMB/CIFS supports it (Linux 3.17). `shell-mcp-gate check-policy` warns, per write root, where it is missing.
- **Descriptions.** "Delete `<path>` on `<target>`", with "and everything under it" for `recursive`; a path that is not plain is "a path shown in the arguments".
- **Audit arguments.** `target`, `path` and `recursive`; never the hash. The gate's audit line logs `path` and `recursive`, not `expected_preview_sha256`.

**Destructive tier: the git discard and the admin `shell_run_command` (S4b-2b).**
- **`shell_discard_git_changes`.** Admin profile only, always approval-gated. The first call sends one `git_discard_preview` at ceiling `destructive` and returns `approval_pending`. The re-call sends `git_discard_preview` again (its hash must equal the approved preview's, else `approval_invalid` and nothing is changed), then `git_discard` with `include_untracked` and `expected_preview_sha256` set to that fresh preview's hash, taken from the gate's answer before the server's redaction. The result is `repo`, `head`, `restore`, `remove`, `untracked`, `entries`, `discarded: true` and `clean_after` (false when untracked files were left without `include_untracked`, or nested repositories exist); a gate answer without `applied` is `internal`, never a success. `expected_preview_sha256` is not a tool input. Ignored files are never removed; HEAD, branches and the stash never change.
- **Discard errors.** `exists`: the repository changed after the fresh preview, before anything was changed ("nothing was changed"), or during the discard ("N of M entries were discarded and K were not; the index was not changed"; preview again to see what remains); or `.git/index.lock` exists (git holds or left it, or a gate stopped while discarding left it; POLICY §7 says how to recover). Nothing that was not in the preview is discarded either way; an entry set aside that could not be put back is named, as for a delete. `policy_denied` (a merge, rebase, cherry-pick, revert or bisect in progress, an unmerged entry, a submodule change, a repository not listed or outside the write roots), `bad_request` (no commits; an entry in the way of a restore, with or without the hint to pass `include_untracked`), `path_denied` (an untracked symlink; the file rules at a listed path) and `too_large` pass through from the preview or the discard.
- **`shell_run_command`: registrations.** In the admin profile it is registered at `destructive` (`destructiveHint: true`, `requiresUserInteraction` in every catalogue variant) and runs commands of tier `read`, `operator` or `destructive`. In the operator profile it keeps its operator registration (`destructiveHint: false`, `requiresUserInteraction` only when `SHELL_MCP_APPROVAL_TIERS` lists `operator`) and runs commands of tier `read` or `operator`; the gate refuses a `destructive` one at ceiling `operator`. `shell-mcp tools` lists both registrations, each with its `profiles`. The annotations are static; whether a call needs approval is not.
- **`shell_run_command`: approval follows the command's tier (D-006).** A `destructive` command always needs approval, an `operator` command only when `SHELL_MCP_APPROVAL_TIERS` lists `operator`, and a `read` command never, in both profiles: the admin profile is never stricter than the operator profile for the same command. Every call first sends `exec_preview` at the tool's ceiling (`destructive` in admin, `operator` in the operator profile), which resolves the command and its tier without running anything. Then:
  - **The tier needs approval:** the approval flow above, with that preview. The re-call sends `exec_preview` again (a different hash, for example after a policy edit or a path placeholder resolving elsewhere, is `approval_invalid` and nothing runs), then `exec` at ceiling = the command's tier, with `expected_preview_sha256`, which the gate checks again before running anything (`exists`). Under `SHELL_MCP_APPROVAL_METHOD=none` the call is `approval_unavailable` after the preview, and nothing runs.
  - **It does not:** `exec` at once, at ceiling = the highest tier that needs no approval (`operator` by default, `read` when the tiers list `operator`), with `expected_preview_sha256`. A policy edit that raises the command's tier between the preview and the exec is refused by the gate's ceiling check (`tier_denied`), which comes before anything else; any other change to what would run is `exists`. An unapproved command can therefore never run above the tiers that need no approval. This holds under every approval method, `none` included.
  - Giving `approval_id` for a command that needs no approval is `approval_invalid` (no such record).
- **Descriptions.** "Discard the uncommitted changes in `<repo>` on `<target>`", with ", untracked files included," for `include_untracked`; "Run command `<id>` with N arguments on `<target>`" as before.
- **Audit arguments.** The discard: `target`, `repo` and `include_untracked`; never the hash (the gate logs `repo` and `include_untracked`). The command: as the operator registration.

**Privileged tier: what the table leaves open (S4c-1).** The read tier's rules on results, input forms, static schema maxima and the redaction order apply here too. The read tools are S4c-1's, the write tools S4c-2's, chown and chmod S4c-3's, the delete tools S4c-4's, restore S4c-5's, the command tool S4c-6's and the package tools S4c-7's (below); the power tool arrives in S4c-8 (`docs/handoff/S4C-PRIVILEGED.md` §5).
- **Registration.** `admin` profile only, with `privileged: true` in the catalogue, at the tier of their section's operation (read for the four read tools). A target whose gate policy does not enable `privileged` forwarding does not serve them (`shell-mcp check` lists them as not effective there). Every description says the tool runs as root.
- **One request, ceiling `read`.** Each read tool validates its input exactly as its unprivileged equivalent (`shell_read_file`, `shell_list_directory`, `shell_stat_path`) and sends one `priv_*` request at ceiling `read`. The gate checks `privileged.enabled` and the tier, and forwards it; the helper re-validates it against the privileged policy (roots, deny list, never list, private-key refusal, `max_read_bytes`) in the core unit. Their results have the unprivileged tools' shapes.
- **Redaction.** The helper redacts with the built-in rules only (the privileged policy has no patterns); the server then applies its built-in rules and `SHELL_MCP_REDACT_PATTERNS`, and its output caps, exactly as for the read tier.
- **Errors.** The helper's refusals pass through with their code and message: `path_denied` (outside the privileged roots, the deny list, the never list, a private key, a final symlink), `bad_request` (`max_bytes` above `max_read_bytes`, a malformed `limit`), `not_found`, `not_a_directory`, `is_a_directory`, `too_large`, `helper_wrong_unit`, and the gate's `privileged_disabled`, `tier_denied`, `helper_unavailable`, `helper_refused`, `timeout` and the `helper_*` self-check codes.
- **Approval (D-006, D9).** Privileged tools of tier operator or above are approval-gated under every configuration, whatever `SHELL_MCP_APPROVAL_TIERS` says: they carry `requiresUserInteraction` in every catalogue variant, and under `SHELL_MCP_APPROVAL_METHOD=none` they refuse with `approval_unavailable` and send nothing. The read tools are never gated. A privileged tool whose gating follows a previewed tier (`shell_priv_run_command`, S4c-6) runs an unapproved operation at ceiling `read`.
- **Binding.** A privileged preview's answers carry the gate's block and the helper's (`helper`, ARCHITECTURE §4.2). The approval record's policy hash is the SHA-256 of `gate:<gate policy SHA-256>\nhelper:<privileged policy SHA-256>`, so an edit of either policy between the approval and the re-call is `approval_invalid`. A privileged preview whose answer has no helper block, or no policy hash in either block, is refused with `internal` and no approval is requested. For a privileged command, its unit is bound through `priv_exec_preview`'s hash (S4c-6).
- **Outcome unknown (`outcome_unknown`; S4c-6, handoff must-fix (b)).** When a privileged operation that can change the host may or may not have run, the result is `outcome_unknown`, never a refusal: every tool below of tier operator or destructive (`shell_priv_write_file`, `shell_priv_make_directory`, `shell_priv_copy_path`, `shell_priv_move_path`, `shell_priv_change_owner`, `shell_priv_set_permissions`, `shell_priv_delete_path`, `shell_priv_restore_backup`, and the four package tools: `shell_priv_update_package_index`, `shell_priv_install_packages`, `shell_priv_upgrade_packages`, `shell_priv_remove_packages`) and `shell_priv_run_command` for an operator or destructive command. It covers an answer lost after the request was sent (the gate's deadline, the helper closing without an answer or answering something unreadable, the server's own time budget, a session closed without an answer), a command the helper stopped because the gate went away, and a command whose leftover processes the helper could not confirm had ended. The message says what to do: the operation may have completed on the host, so check there (preview again, or read the helper's journal and the backups) before retrying; the approval was used (the approval object says `used`), so a retry needs a new approval; then the cause. A read tool's errors, an unapproved read command's `timeout`, and the helper's `timeout` for a command it never started ("nothing was run") stay as they were.
- **Audit arguments.** `target` and `path`. The gate's and the helper's audit lines for the same request join on its id.

**Privileged tier: the write tools (S4c-2).** `shell_priv_write_file`, `shell_priv_make_directory`, `shell_priv_copy_path` and `shell_priv_move_path`.
- **Registration and gating.** Admin profile only, at `operator`, with `privileged: true`. Annotations: `readOnlyHint: false`, `destructiveHint: true` (they change root-owned state), `openWorldHint: true`, and `idempotentHint` true for write (the same content again), mkdir (a repeat is `exists`) and copy, false for move. Always approval-gated (D-006): `approval_id`, and `confirm` under `confirm-argument`, in every configuration, with `requiresUserInteraction`; under `SHELL_MCP_APPROVAL_METHOD=none` every call is `approval_unavailable` and nothing is sent.
- **Inputs.** As the operator tools (`shell_write_file`, `shell_make_directory`, `shell_copy_path`, `shell_move_path`), plus `owner` and `group` on write and mkdir: user and group names (`^[a-z_][a-z0-9_-]{0,31}$`), which the helper requires to be on its `owners` lists (`policy_denied` otherwise, at the operation). A requested `mode` must be within `modes.max` (`policy_denied` at the operation); without one, an existing file keeps its mode and a new one gets `0640` (a directory `0750`), each masked by `modes.max`, so a file wider than the mask is narrowed when it is written or copied over, and the result reports the mode set. A new file, copy or directory without an owner is root's (`root:root`), whether or not root is on the allow-list (PRIVILEGED §6).
- **Previews**, composed from the helper's read ops at ceiling `operator` (handoff D2) and bound with both policies' hashes:

  | Tool | Helper reads | Preview |
  |---|---|---|
  | `shell_priv_write_file` | `priv_stat`, `priv_read_file` (an existing file's SHA-256), `priv_backup_check` | `path`; `current`: `{state: absent}`, or `{state: file, type, size, mode, uid, gid, owner?, group?, sha256, lines}`; `new`: `{bytes, sha256, lines}`; `lines_delta`; `set`: `{owner, group, mode}`, the values requested or, in words, what the helper does without one ("kept: the file's current owner", "root (a new file without an owner is root's)", "0640, masked by the host's modes.max"); `backup`: `{written, bytes}`. |
  | `shell_priv_make_directory` | `priv_stat` of the path and, with `parents`, of each missing ancestor up to the first that exists (at most 64), `priv_backup_check` (the write-root check) | `path` (absent, or its stat); `create`: the directories that will be created, top down; `set`: `{owner, group, mode}` as above. |
  | `shell_priv_copy_path`, `shell_priv_move_path` | `priv_stat` of the source and of the destination, `priv_read_file` of an existing destination, `priv_backup_check` | `source` (its stat); `destination`: `{state: absent}` or `{state: file, type, size, mode, uid, gid, owner?, group?, sha256}`; `overwrite`; for a copy, `set`: `{owner, group, mode}` ("root (a new copy is root's)" and "the source's mode, without setuid, setgid, sticky and world-write, masked by the host's modes.max", or over a file "kept: the destination's current owner" and "the destination's current mode, masked by the host's modes.max", so the approver sees when root-only content would land in a more readable file); `backup`. |

  `priv_backup_check` (PRIVILEGED §6) says whether the operation would back up what it replaces and whether that backup fits the store's cap; the store's moving byte counts are never part of a preview (it must hash the same at the re-call).
- **Refused at the preview, with no approval requested:** a path outside the privileged write roots, on the deny list or in the protected set (`path_denied`, from `priv_stat` or `priv_backup_check`); a final symlink at the path, source or destination (`path_denied`); a write over, or a copy onto, a directory (`is_a_directory`); a move onto a directory, or of a directory onto anything (`exists`: directories are never replaced); a copy of a directory (`is_a_directory`); a destination that exists without `overwrite` (`exists`); a mkdir whose directory exists, without `parents` (`exists`), or whose parent is missing, without `parents` (`not_found`); a file the helper gives no SHA-256 for (above 256 MiB: `too_large`, as an overwrite could not be bound); a backup over 64 MiB, or one that would take the store over `backups.max_store_bytes` (`backup_failed`, "the backup store is full (N of M bytes used) …"). What only the helper's policy knows (an owner off the allow-list, a mode outside the mask, a source over `max_read_bytes`) is refused at the operation, after the approval, and changes nothing.
- **Files another account could have moved in (S4c-5).** The helper reads, and keeps the owner of, a file under a directory another account could write only when that account could have read or written it itself (PRIVILEGED §6, "Files another account could have moved in"). The previews hash an existing destination through `priv_read_file`, so an overwrite of a file the read rule refuses is refused at the preview (`path_denied` naming the directory), with no approval requested, even with an explicit owner. A world-readable file there whose owner may not be inherited is refused at the operation, after approval, changing nothing: a write needs both `owner` and `group`; a copy over it, which has no owner inputs, is refused; a copy from a source the read rule refuses is refused too.
- **Re-call and preconditions.** The fresh preview must hash as approved (`approval_invalid` otherwise: the target, the destination, the gate policy or the privileged policy changed). Then what it saw is passed on: a write sends `expected_sha256` of the content it saw (a caller's own is kept), or `expect_absent` when it saw no file; a copy or move with `overwrite` sends `expected_destination_sha256` of the destination it saw (P-9), or is sent with `overwrite: false` when it saw none, so an approved overwrite never replaces a file that appeared. In the helper every replace is an exchange checked afterwards (PRIVILEGED §6, verified replaces), so a destination changed between the fresh preview and the commit is refused with `exists` and kept. `expect_absent` and `expected_destination_sha256` are not tool inputs.
- **Results.** Write: `path`, `created`, `bytes`, `mode`, `uid`, `gid`, `owner?`, `group?`, `old_sha256`, `new_sha256`, `lines_old`, `lines_new`, `lines_delta`, `owner_preserved`, `backup_ids`. Mkdir: `path`, `created`, `mode`, `uid`, `gid`, `owner?`, `group?`. Copy: `source`, `destination`, `created`, `bytes`, `mode`, `uid`, `gid`, `owner?`, `group?`, `sha256`, `old_sha256`, `backup_ids`. Move: `source`, `destination`, `type`, `replaced`, `backup_ids`. `mode`, `uid` and `gid` are what the helper set, read from the new inode's descriptor; `owner` and `group` are names on the privileged policy's `owners`. Write and copy set the envelope's `verified: true`; an answer without a confirmed read-back is `verify_failed`, never a success.
- **Errors.** The helper's refusals pass through: `path_denied`, `policy_denied`, `exists`, `not_found`, `is_a_directory`, `not_a_directory`, `too_large`, `backup_failed`, `verify_failed`, `bad_request` (a filesystem without `RENAME_EXCHANGE`, which replacing a file as root needs, or without hard links or `RENAME_NOREPLACE` for a create-only commit), and the gate's and helper's codes listed above.
- **Descriptions.** "As root, write N bytes to `<path>` on `<target>`"; "As root, create directory `<path>` [and its missing parents] on `<target>`"; "As root, copy (move) `<source>` to `<destination>`[, replacing an existing destination,] on `<target>`"; a path that is not plain is "a path shown in the arguments".
- **Audit arguments.** As the operator tools, plus `owner` and `group`; never content or hashes.

**Privileged tier: chown and chmod (S4c-3).** `shell_priv_change_owner` and `shell_priv_set_permissions`.
- **Registration and gating.** As the write tools: admin profile only, at `operator`, with `privileged: true`, `readOnlyHint: false`, `destructiveHint: true`, `idempotentHint: true`, `openWorldHint: true`; always approval-gated (D-006), with `requiresUserInteraction` in every catalogue variant; under `SHELL_MCP_APPROVAL_METHOD=none` every call is `approval_unavailable` and nothing is sent.
- **Inputs.** `path`; `owner` and/or `group` (names, `^[a-z_][a-z0-9_-]{0,31}$`, at least one; the helper requires each to be on its `owners` lists) or `mode` (3 or 4 octal digits; within `modes.max`, never setuid, setgid, sticky or world-write); `recursive` (default false): also everything under a directory, up to the privileged policy's `max_delete_entries` entries. `expected_preview_sha256` is not a tool input.
- **Preview** (the helper's `priv_chown_preview` or `priv_chmod_preview`, at ceiling `operator`, bound with both policies' hashes): `path`, `recursive`, `type`, `entries`, `changes` (entries that change: the others already have the values asked for, or are symlinks, which are never changed), `first` (at most 50 entries in walk order, each with `path`, `type`, `uid`, `gid`, `owner?`, `group?`, `mode`, `new_uid`, `new_gid`, `new_owner?`, `new_group?`, `new_mode`), `truncated`, `set` (`{owner, group}`, "kept" for the one not given, or `{mode}`) and `preview_sha256`. The hash covers the change, the privileged policy and every entry's identity, owner, group and mode (PRIVILEGED §6), so anything that would change what happens changes it, beyond the first 50 too; a content write does not.
- **Refused at the preview, with no approval requested:** a path outside the privileged write roots, denied or protected, a write root itself or a tree holding one, a final symlink, a mount point or a tree holding one, a device node, FIFO or socket in a tree (`path_denied`; a special file as the target is `bad_request`); a file or directory with setuid, setgid or sticky bits (`policy_denied`); a non-directory with more than one link anywhere in the walk (`path_denied`, naming it and the count); a path, or a tree, under a directory that an account other than root owns or that is group- or world-writable (`path_denied`, naming the directory: another account could have moved the entry in, PRIVILEGED §6); an owner, group or mode the policy does not allow (`policy_denied`); more than `max_delete_entries` entries (`too_large`).
- **Application-owned trees.** Once a tree has been chowned to an application account, every later chown or chmod inside it is refused at the preview, a second `recursive` chown of the same tree included: its directories are that account's now, and the chain rule refuses anything another account could have moved in (PRIVILEGED §6). The intended way to manage such trees is a fixed root command template that the operator writes into the privileged policy and runs through `shell_priv_run_command` (S4c-6), which still needs approval.
- **Re-call.** The fresh preview must hash as approved (`approval_invalid` otherwise: the tree, an owner or mode in it, either policy changed). Then the operation is sent with that preview's `preview_sha256` (taken from the helper's answer before the server's redaction) as `expected_preview_sha256`: the helper walks again and changes exactly that plan or nothing (`exists`); an entry changed during the operation stops it with `exists`, "N of M entries were changed and K were not" (preview again to see what remains). Each change is read back through the descriptor it was made on; a mismatch is `verify_failed`.
- **Results.** Owner: `path`, `recursive`, `entries`, `changed` (the approved preview's counts, all of which the success confirms), `uid`, `gid` (the target's now), `owner?`, `group?` (the names set). Mode: `path`, `recursive`, `entries`, `changed`, `old_mode`, `mode` (the target's).
- **Errors.** The refusals above, at the preview or the operation, and `exists`, `verify_failed`, `not_found`, and the gate's and helper's codes listed above.
- **Descriptions.** "As root, change the owner and group of `<path>` [and everything under it] to `<owner>:<group>` on `<target>`" (or "the owner of … to `<owner>`", "the group of … to `<group>`"); "As root, set the mode of `<path>` [and everything under it] to `<mode>` on `<target>`"; a path that is not plain is "a path shown in the arguments".
- **Audit arguments.** `target`, `path`, `recursive`, and `owner`, `group` or `mode`; never the hash. The helper's journal line lists the entries changed with their old values (PRIVILEGED §8).

**Privileged tier: delete (S4c-4).** `shell_priv_preview_delete` and `shell_priv_delete_path`.
- **Registration and gating.** Admin profile only, with `privileged: true`. `shell_priv_preview_delete` is read tier (read annotations, never gated; its one request is sent at ceiling `read`). `shell_priv_delete_path` is destructive tier: `readOnlyHint: false`, `destructiveHint: true`, `idempotentHint: false`, `openWorldHint: true`; always approval-gated (D-006), with `requiresUserInteraction` in every catalogue variant; under `SHELL_MCP_APPROVAL_METHOD=none` every call is `approval_unavailable` and nothing is sent.
- **Inputs.** `path`, and `recursive` (default false): also everything under a directory, up to the privileged policy's `max_delete_entries`. `expected_preview_sha256` is not a tool input.
- **Preview** (the helper's `priv_delete_preview`; for the delete, at ceiling `destructive`, bound with both policies' hashes): `path`, `recursive`, `type`, `entries`, `bytes`, `first` (at most 50 entries, the path first, then depth-first in byte order of names), `truncated`, `backup` (`{written, kind, bytes}`: `written` false when the privileged policy keeps no backups; `kind` `file` or `tree`; `bytes` the backup's size, the file's or the tree's archive) and `preview_sha256`. The hash covers the privileged policy and every entry's path, type, size and identity (PRIVILEGED §6, "Delete"), beyond the first 50 too.
- **Refused at the preview, with no approval requested:** a path outside the privileged write roots, denied or protected, a write root itself or a tree holding one, a final symlink, a mount point or a tree holding one, a device node or a tree holding one, a name starting with `.shell-mcp-delete-` (an entry an earlier delete left set aside) or a tree holding one (`path_denied`); a non-empty directory without `recursive` (`bad_request`); more than `max_delete_entries` entries (`too_large`); with backups on, a tree holding a symlink, FIFO or socket, or such a file as the path, a backup over 64 MiB, or one that would take the store over `backups.max_store_bytes` (`backup_failed`). A hard-linked file is not refused: its name under the write root is removed, and its other names keep the file.
- **Re-call.** The fresh preview must hash as approved (`approval_invalid` otherwise: the tree, or either policy, changed, and nothing is deleted). Then `priv_delete` is sent with that preview's `preview_sha256` (taken from the helper's answer before the server's redaction) as `expected_preview_sha256`: the helper walks again and refuses with `exists`, deleting nothing, unless it hashes the same; it backs up exactly that plan, then deletes exactly it. An entry replaced or changed while it is being backed up, or after, stops the delete with `exists` ("nothing was deleted", or "N of M entries were deleted and K were not"; preview again to see what remains); nothing outside the preview is ever deleted. An entry that could not be put back under its name is left under `.shell-mcp-delete-<32 hex>`, named in the message, never deleted (POLICY §3).
- **Results.** Preview: as above. Delete: `path`, `type`, `entries`, `bytes`, `deleted: true` and `backup_ids` (empty with backups off); a helper answer without `deleted` is `internal`, never a success. The backup restores with `shell_priv_restore_backup` (S4c-5).
- **Errors.** The refusals above, at the preview or the delete, and `exists`, `not_found`, `backup_failed`, `bad_request` (a filesystem without `RENAME_NOREPLACE`), and the gate's and helper's codes listed above.
- **Descriptions.** "As root, delete `<path>` [and everything under it] on `<target>`"; a path that is not plain is "a path shown in the arguments".
- **Audit arguments.** `target`, `path` and `recursive`; never the hash. The helper's journal line lists the entries removed and the backup ids (PRIVILEGED §8).

**Privileged tier: restore (S4c-5).** `shell_priv_restore_backup`.
- **Registration and gating.** Admin profile only, at `operator`, with `privileged: true`. Annotations: `readOnlyHint: false`, `destructiveHint: true`, `idempotentHint: false`, `openWorldHint: true`. Always approval-gated (D-006), with `requiresUserInteraction` in every catalogue variant; under `SHELL_MCP_APPROVAL_METHOD=none` every call is `approval_unavailable` and nothing is sent. There is no separate read-tier preview tool (handoff Q7 names delete and packages only); `shell_priv_list_backups` lists what can be restored.
- **Inputs.** `backup_id` (`YYYYMMDDTHHMMSSZ-<16 hex>`, as `shell_priv_list_backups` shows it). `expected_preview_sha256` is not a tool input.
- **Preview** (the helper's `priv_restore_preview`, at ceiling `operator`, bound with both policies' hashes): `id`, `kind` (`file` or `tree`), `path`; `backup`: `{size, sha256, entries, uid, gid, owner?, group?, mode, created, op}` (the recorded values); `current`: `{state: absent}` or `{state: file, size, mode, uid, gid, owner?, group?, sha256}`; `restore`: `{uid, gid, mode, recorded_mode, narrowed, first, truncated}` (the owner, group and mode that will be set, the mode recorded, how many entries the host's `modes.max` narrows, and for a tree the first 50 entries with `path`, `type`, `recorded_mode` and `mode`); `current_backup`: `{written, bytes}`; and `preview_sha256`. The hash covers the backup's record, what will be set, the current state at the path and the privileged policy (PRIVILEGED §6, "Restore"). No content is ever shown.
- **Refused at the preview, with no approval requested:** an unknown id, or backups disabled (`not_found`); a backup whose data does not match its recorded size and SHA-256, or a tree archive that does not hold its recorded entries (`verify_failed`); a path no longer under a privileged write root, denied or protected, or a symlink there (`path_denied`); a file restore over a directory (`is_a_directory`), another non-file (`bad_request`), or a file with setuid, setgid, sticky or world-write bits (`policy_denied`); a tree restore where anything exists (`exists`); a current version whose backup would exceed 64 MiB or the store's cap (`backup_failed`); more than `max_delete_entries` entries in a tree (`too_large`); a restore whose recorded owner another account could take, or over a file another account could have moved in and could not read itself (`path_denied` naming the directory; PRIVILEGED §6, "Files another account could have moved in").
- **Re-call.** The fresh preview must hash as approved (`approval_invalid` otherwise: the backup, the file at its path, or either policy changed, and nothing is restored). Then `priv_restore_backup` is sent with that preview's `preview_sha256` (taken from the helper's answer before the server's redaction) as `expected_preview_sha256`: the helper reads and verifies the backup again (`verify_failed` if it was changed since), recomputes the preview and refuses with `exists`, restoring nothing, unless it hashes the same. A file is written over exactly the file the preview saw (a verified replace; one changed in the last moment is `exists` and kept), or create-only when the preview saw none, after backing up the current version. A tree is created only where nothing exists, every directory exclusively and every file create-only; an entry that appeared meanwhile stops it with `exists`, "N of M entries were restored and K were not".
- **Results.** `id`, `path`, `kind`, `sha256` (a file's, read back), `entries` (a tree's), `backup_ids` (the current version's backup, restorable in turn), `mode` and `recorded_mode` (the file's or the tree root's), `narrowed`, and for a tree `first` (at most 50 entries with `path`, `type`, `recorded_mode` and `mode`) and `truncated`. The envelope's `verified` is true; an answer without a confirmed read-back is `verify_failed`, never a success.
- **Errors.** The refusals above, at the preview or the restore, and `exists`, `verify_failed`, `backup_failed`, `not_found`, `bad_request` (a filesystem without `RENAME_EXCHANGE` or hard links), and the gate's and helper's codes listed above.
- **Descriptions.** "As root, restore backup `<id>` on `<target>`" (the path is in the preview).
- **Audit arguments.** `target` and `backup_id`; never the hash. The helper's journal line carries the backup id and the id of the current version's backup (PRIVILEGED §8).

**Privileged tier: commands (S4c-6).** `shell_priv_run_command`.
- **Registration.** Admin profile only, at `destructive`, with `privileged: true`. Annotations: `readOnlyHint: false`, `destructiveHint: true`, `idempotentHint: false`, `openWorldHint: true`; `requiresUserInteraction` in every catalogue variant, since its operator and destructive commands are always gated.
- **Inputs.** `command_id`, `args` (at most 64, each at most 1024 bytes, no NUL or line breaks), `cwd?` (absolute and clean, under a privileged root; default `/`), `timeout_seconds?`, `max_output_bytes?` (at most the server's limit; the privileged policy's `max_output_bytes` applies on the host). No `stdin`: root commands always read `/dev/null` (handoff Q11; the privileged policy declares no stdin limit). The routing label `unit` and `expected_preview_sha256` are not inputs.
- **The preview first** (the helper's `priv_exec_preview`, at ceiling `destructive`, through the core socket for commands of either unit, bound with both policies' hashes): `command_id`, `tier`, `unit` (`core` or `broad`), `description`, `root_equivalent`, `capabilities`, `template` (the template the arguments matched), `argv` (the resolved binary and arguments, path placeholders resolved on the host), `cwd` (resolved) and `preview_sha256`. It runs nothing. An undeclared command (`policy_denied`), a command above the privileged policy's `max_tier` (`tier_denied`), arguments matching no template (`template_mismatch`) or a refused path (`path_denied`: outside the privileged roots, denied, a final symlink, or a placeholder or `cwd` with a directory from `/` to its parent, or a directory placeholder or `cwd` itself, that an account other than root owns or can write, or that is sticky; PRIVILEGED §6, "Commands") are the result, and no approval is requested; an answer without the helper block, or naming no known unit or tier, is `internal`.
- **Gating follows the command's tier** (D-006, D9): read commands never need approval; operator and destructive commands always do, under every `SHELL_MCP_APPROVAL_TIERS`.
  - **A read command** is sent at once as `priv_exec` at ceiling `read`, with the preview's `unit` and `preview_sha256` as `expected_preview_sha256`; a command whose tier rose after its preview is refused by the helper's tier check (`tier_denied`), and any other change to what would run is `exists`. This holds under every approval method, `none` included.
  - **An operator or destructive command** goes through the approval flow with that preview (under `SHELL_MCP_APPROVAL_METHOD=none`: `approval_unavailable` after the preview, and nothing runs). The re-call previews again (another hash, unit, tier or either policy is `approval_invalid`, and nothing runs), then sends `priv_exec` at ceiling = the command's tier, with the fresh preview's `unit` and `preview_sha256` (taken from the helper's answer before the server's redaction), which the helper there recomputes before running anything (`exists`).
  - Giving `approval_id` for a read command is `approval_invalid` (no such record).
- **Routing (Q5).** `priv_exec` goes to the unit the fresh preview reported, and only there: an instance's `helper_wrong_unit` (the command moved to the other unit between the preview and the run) is the tool's result, never retried in the other unit; calling the tool again previews afresh, and a gated command then needs a new approval.
- **Results.** As `shell_run_command`: `command_id`, `argv` (as the helper ran it), `stdout` and `stderr` (redacted by the helper's built-in rules and then the server's, capped), their truncation flags and `duration_ms`, with the exit status in the envelope's `exec` block; a non-zero exit is a success. An approved command stopped at its timeout (`exec.timed_out`) carries a warning that what it changed before then is unknown.
- **Timeouts and lost answers.** The helper stops the command at its timeout, and also when the gate goes away or stops waiting, killing everything the command started before it answers (PRIVILEGED §6, "Timeouts, and a gate that goes away"). For an operator or destructive command, a stop by the gate's hang-up, a lost answer, or leftovers the helper cannot confirm ended are `outcome_unknown` ("Privileged tier: what the table leaves open", above); a read command stopped the same way is `timeout`.
- **Errors.** The preview's refusals above, `exists` (the command resolves differently than its approved preview), `tier_denied`, `helper_wrong_unit`, `outcome_unknown` (an approved command that may have run), `timeout` (a read command stopped, or a command never started), `exec_failed` (the command could not be started), and the gate's and helper's codes listed above.
- **Descriptions.** "As root, run command `<id>` with N arguments in the `<unit>` unit on `<target>`".

**Privileged tier: packages (S4c-7).** `shell_priv_preview_packages`, `shell_priv_update_package_index`, `shell_priv_install_packages`, `shell_priv_upgrade_packages`, `shell_priv_remove_packages`. They run apt as root in the helper's broad unit (PRIVILEGED §6, "Package operations"); installing, upgrading or removing a package runs its maintainer scripts as root.
- **Registration.** Admin profile only, with `privileged: true`. `shell_priv_preview_packages` is read tier (read annotations, never gated, one request at ceiling `read`). The update, install and upgrade tools are registered at `operator`, the remove tool at `destructive`; all four have `readOnlyHint: false`, `destructiveHint: true`, `idempotentHint: false`, `openWorldHint: true`, and are always approval-gated (D-006), with `requiresUserInteraction` in every catalogue variant; under `SHELL_MCP_APPROVAL_METHOD=none` every call is `approval_unavailable` and nothing is sent.
- **Inputs.** Package names only (`packages`, 1..20, each a Debian package name of at most 128 bytes: lower-case letters, digits, `+`, `-`, `.`, at least two characters, alphanumeric first; no duplicates), and `timeout_seconds?`. Never an apt option, a source, a key, a version, or a path to a `.deb`; the helper also checks each name against the privileged policy's allow-list.
- **The preview** (the helper's simulation, bound with both policies' hashes): `op`, `packages`, `install` (name, version), `upgrade` (name, from, to), `remove` (name, version, purge), `argv` and `preview_sha256`; for the index update, the action only (`argv`, no apt sources). Refused, with no approval requested: a name not on the allow-list (`policy_denied`), an install or upgrade that would remove a package (`policy_denied`), a simulation that failed or did not parse (`exec_failed`), packages dpkg left unfinished (`exec_failed`, with the recovery an administrator runs on the host, `dpkg --configure -a`), a package operation still in progress or the package database locked by another process (`exec_failed`, naming the request id and the time it may run until, or the lock's holder).
- **The re-call** previews again (another transaction, version or policy is `approval_invalid`), then sends the operation with the fresh preview's `preview_sha256`. The helper simulates again, the preview's argv and then the exact pinned argv it will run, and refuses with `exists`, running nothing, if either differs from the approved transaction; it never runs `apt-get upgrade` at run time, only the approved list.
- **Results.** `op`, `packages`, `applied` (what dpkg's status shows was installed, upgraded and removed, with versions), `exit_code`, the redacted, capped `stdout` and `stderr` and their truncation flags, `attempts`, `lock_wait_ms` and `duration_ms` (the index update: no `applied`). The result is decided by dpkg's status, never by apt's exit code: exactly the approved transaction is a success; nothing changed is `exec_failed` (quoting apt's error lines); anything else — part of it, a different transaction, or packages left unfinished — is `verify_failed`, naming what was applied and, for unfinished packages, the recovery.
- **Lock.** A dpkg lock held by another process (for example unattended-upgrades) is waited for, at most `min(60 s, timeout / 2)`, then `exec_failed` naming the holder; nothing was changed, and the approval was used.
- **Timeouts and lost answers.** Install, upgrade and remove are the one exception to "stopped when the gate goes away" (PRIVILEGED §6): at the timeout, or when the gate goes away, apt is left to finish, and the result is `outcome_unknown` at once, naming the request id and the UTC time it may run until; the helper stops apt gracefully before its own limit and kills it only at that limit, and its journal line under the request id records what changed. Preview again after that time (a preview says "package operation in progress" until then). The index update is stopped like a command, also `outcome_unknown`. A timeout before apt started is `timeout`, "nothing was changed".
- **Errors.** The preview's refusals above, `exists` (the transaction changed since the approved preview), `verify_failed`, `exec_failed`, `outcome_unknown`, `timeout`, `tier_denied`, `helper_wrong_unit`, and the gate's and helper's codes listed above.
- **Descriptions.** "As root, install N packages on `<target>`", "As root, upgrade N packages on `<target>`" (from the preview), "As root, remove N packages on `<target>`", "As root, update the package index on `<target>`".
- **Audit arguments.** As `shell_run_command`: `target`, `command_id`, `args_count` and `cwd`; never the arguments or the hash. The helper's journal line carries the command id, the argument count, the `cwd` and the unit label, at WARN in the broad unit, and `hung_up: true` when the gate went away while the command ran (PRIVILEGED §8).

## Not in v1

A diagnostic tool, `shell_diag_elicit` (asks a harmless yes/no question through elicitation and reports what the client did), exists only in a binary built with the `shellmcp_diag` tag for local client testing; release builds and the image never contain it, and CI fails a cross-built binary that carries the tag.

Package managers other than apt, streaming/follow modes, file upload/download of binaries, archive extraction, container tools (use a container-manager MCP), anything in `docs/SECURITY.md` §4.

## Error contract

Every tool returns the envelope from `docs/ARCHITECTURE.md` §6. A non-zero process exit from `shell_run_*` is `ok: true` with `exec.exit_code` set; structured tools (`shell_git_pull`, `shell_control_service`) map a failed underlying command to `ok: false` with the gate's code and the exit status in `error.message`.
