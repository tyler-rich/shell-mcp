# Tool catalogue (v1 contract)

Conventions: names are `shell_<verb>_<noun>`. Every tool takes `target: string` (optional when exactly one target exists or `SHELL_MCP_DEFAULT_TARGET` is set). **Gate op** is the operation in `docs/ARCHITECTURE.md` §4.3; the gate enforces the policy for it independently of this table.

Annotations: `read` → `readOnlyHint: true, destructiveHint: false, idempotentHint: true, openWorldHint: true`. `operator` → `readOnlyHint: false, destructiveHint: false, openWorldHint: true` (`idempotentHint` per tool). `destructive` → `readOnlyHint: false, destructiveHint: true, idempotentHint: false, openWorldHint: true`. Every tool sets `title` and an `outputSchema`.

Common optional inputs on tools that run a process: `timeout_seconds` (1..`SHELL_MCP_MAX_TIMEOUT`, default `SHELL_MCP_DEFAULT_TIMEOUT`), `max_output_bytes` (1..`SHELL_MCP_MAX_OUTPUT_BYTES`).

**Profiles.** `read-only` registers the read tier; `operator` adds the operator tier; `admin` adds the destructive and privileged tiers — `admin` is the profile for a fully capable deployment. Each host's gate and privileged policies still decide what actually runs.

**Tier ceiling.** Every gate request a tool makes carries the tool's registered tier (the tier of its section below) as the request's `ceiling` (ARCHITECTURE §4.1). The gate, and the helper for `shell_priv_*` tools, refuse any operation or command above min(their policy's `max_tier`, `ceiling`) with `tier_denied`, in one check before anything runs. So a tool can never act above its own tier on a host, even through a server mistake or a policy edited between two requests, and a profile's tools are bounded on the host as well as by registration. The ceiling does not defend against a compromised server, which can send any ceiling; the host policies are the boundary for that.

**Approval (D-006).** Destructive tools, privileged tools of tier operator or above, and any tier listed in `SHELL_MCP_APPROVAL_TIERS` are approval-gated. How approval is collected is `SHELL_MCP_APPROVAL_METHOD`:
- **`web` (out-of-band).** The first call computes a preview and returns `approval_pending` (`ok: false`, nothing ran) with an `approval` object `{id, status, url, expires_at, summary}`. Its message tells the model to show the user the URL exactly as written. The approver opens the approval page from a bookmark (entering the id) or from the server's own optional push, never from a link in the chat; checks the origin banner, the server's description, the arguments and the preview; and approves or declines with a current TOTP code from their authenticator. The approval page can be opened on any device; only the code must come from the approver's authenticator. The model then calls the tool again with the same arguments plus `approval_id`, and the server runs exactly that operation, once.
- **`confirm-argument`.** The same record and binding, but the re-call carries `approval_id` and `confirm: true`, and the server records the approver as `model (confirm-argument)`, with a WARN at startup and on every use. **This turns approval off against a prompt-injected model**: the model chooses the argument.
- **`none` (the default).** Approval-gated tools refuse with `approval_unavailable` and send nothing.

**Approval codes.** `approval_pending`: approval is required or still awaited (a re-call while the record is pending waits up to 20 s, then answers this again). `approval_declined`: the approver declined. `approval_invalid`: the id is unknown, expired, already used, or does not match the call (principal, tool, target, arguments), or the target or its policy changed since approval (the fresh preview's or policy's hash differs); request a new approval. `approval_unavailable`: the method is `none`, or too many approvals are pending for this principal (5), or the store is full.

**Approval inputs and metadata.** Every tool that can be approval-gated (operator and destructive tiers) has an optional `approval_id` input (26 characters, `^[a-z2-7]{26}$`), whatever the configuration, so the catalogue does not depend on it; on a call that needs no approval, giving one is a `validation_error`. Under `confirm-argument`, and only then, those tools also have a `confirm` input. Approval-gated tools carry `_meta["anthropic/requiresUserInteraction"]: true`, so Claude Code shows their permission prompt on every call, without "always allow". That is client-side defence in depth, not approval: the server cannot verify it.

**Read tier: what the table leaves open (S3).**
- **Results.** `structuredContent` is the envelope. The text block is one summary line (`ok: <counts and flags>` or `error: <code>`), which never carries a string from the host or the caller, followed by the same envelope JSON, so a client that passes only text to the model still sees the data. Host content (files, logs, diffs, command output, process lines, names) is data in envelope fields, never phrased as instructions.
- **Common inputs.** `timeout_seconds` is accepted by the tools that start a process on the target: `shell_get_service_status`, `shell_list_services`, `shell_get_journal`, `shell_get_git_status`, `shell_get_git_log`, `shell_get_git_diff` and `shell_run_read_command`. `max_output_bytes` is accepted by the tools that return free text: `shell_get_journal`, `shell_get_git_diff` and `shell_run_read_command`. Other tools use the server default timeout.
- **Bounds.** Schema maxima are static, so the catalogue is the same for every deployment. Where a bound depends on a setting, the schema gives the highest value that setting can take: `timeout_seconds` ≤ 3600, `max_output_bytes` and `max_bytes` ≤ 4194304, `lines` ≤ 10000, `max_depth` ≤ 32, find `limit` ≤ 10000. The configured value then applies: `SHELL_MCP_MAX_TIMEOUT` and `SHELL_MCP_MAX_OUTPUT_BYTES` are checked by the server (`validation_error`), and policy limits are checked by the gate (`bad_request`). An optional integer that is given must be in range: `0` is refused, never read as "default". An omitted one takes the default in the table.
- **Input forms.** Paths (`path`, `root`, `repo`, `cwd`) must be absolute and already clean; they are refused, never cleaned. `unit` is an exact name with a type suffix. `since`/`until` are as in the table, and `since` may not be after `until`. `modified_within` is `N` followed by `s`, `m`, `h`, `d` or `w` (`30m`, `2d`), at most ten years. `user` is a user name or a numeric uid. Filters (`name_contains`, `name_glob`) are at most 256 bytes; `name_glob` has no `/`. `offset` and `tail_lines` may not both be given. `args` holds at most 64 items, each at most 1024 bytes, with no NUL, CR or LF. `command_id` matches the policy's id pattern.
- **Output bounds and redaction order.** The gate caps and redacts first, with its built-in rules and the policy's patterns. The server then redacts every string in the data and every warning with its built-in rules and `SHELL_MCP_REDACT_PATTERNS`. It cuts each free-text field (journal output, diff, file content, stdout, stderr) to `max_output_bytes` (default `SHELL_MCP_MAX_OUTPUT_BYTES`), redacting before the cut and again after it, and never inside a UTF-8 sequence. Last, it drops trailing entries of a list (mounts, processes, units, directory and find entries, git status entries, commits, certificates) until the data fits `SHELL_MCP_MAX_OUTPUT_BYTES`. Every cut sets the tool's `truncated` flag (for commands, `stdout_truncated`/`stderr_truncated` in `data` and in `exec`).
- **`shell_run_read_command`.** It sends one `exec` request at ceiling `read`. The gate refuses a `command_id` that is not declared (`policy_denied`) and a command whose tier is above `read` (`tier_denied`, its message naming the ceiling) in the same check that applies its `max_tier`, before anything is executed; it then matches the templates. The tool does not read the policy first, so there is no window between a tier check and the run. A non-zero exit is `ok: true` with `exec.exit_code`.
- **Audit arguments.** The audit arguments are `target`, plus `path`, `recursive`, `root`, `repo`, `unit`, `command_id`, `cwd`, and `args_count` (the number of `args`, never their values). Filters, times and content are never logged.

## Operator tier (profile ≥ `operator`, policy `max_tier` ≥ `operator`)

| Tool | Gate op | Inputs | Notes | Session |
|---|---|---|---|---|
| `shell_control_service` | `service_control` | `target`, `unit`, `action: start\|stop\|restart\|reload` | polkit-authorized; returns the post-action status (re-read). `idempotentHint: false`. | S4a |
| `shell_write_file` | `write_file` | `target`, `path`, `content` (UTF-8, ≤ `max_write_bytes`), `mode?` (octal string), `create=true`, `expected_sha256?` | Atomic. **Read-back verified** — `verified: false` is a failure. `expected_sha256` = optimistic concurrency against the current content (refuses if the file changed since the caller read it). An approved write whose preview saw no file is sent with the gate's `expect_absent`, so it never replaces a file that appeared since (`exists`). Returns old/new SHA-256 and a line-count diff summary (never content). | S4a |
| `shell_make_directory` | `mkdir` | `target`, `path`, `mode?`, `parents=false` | | S4a |

| `shell_move_path` | `move` | `target`, `source`, `destination`, `overwrite=false` | Both ends under write roots; same filesystem only (rename). Without `overwrite`, a destination that exists at the moment of the rename is refused with `exists` (`RENAME_NOREPLACE`); a filesystem without it is refused, not moved by check-then-rename. | S4a |

In the `admin` profile this tool also accepts `destructive` commands (approval required) and is registered with `destructiveHint: true`. | S4a / S4b |

**Operator tier: what the table leaves open (S4a).** The read tier's rules on results, input forms, static schema maxima and the redaction order apply here too.
- **One request, ceiling `operator`.** Each tool validates its input, sends one gate request of its op at ceiling `operator` and shapes the result. The gate re-validates everything against its policy: write roots, the deny list, the protected set (`.git` included), modes, units and verbs, repositories and remotes, command tiers and templates. `shell_run_command` is registered at `operator` in both the operator and the admin profile until S4b adds its admin registration at `destructive` (with approval), so today it runs commands of tier `read` or `operator` only, and the gate refuses a `destructive` command with `tier_denied` naming the ceiling.
- **`idempotentHint`.** True when repeating the call with the same arguments changes nothing more on the host: `shell_write_file` (the same content again; with `expected_sha256` a repeat is refused), `shell_make_directory` (a repeat is `exists`), `shell_copy_path` (a repeat is `exists`, or the same copy with `overwrite`) and `shell_set_permissions`. False for `shell_control_service` (every call acts on the unit again), `shell_git_pull` (a later call can fetch new commits), `shell_run_command` (any declared command) and `shell_move_path` (a repeat finds the source gone; it is not safe to retry blindly, since a source recreated in between would be moved again).
- **Write results.** `shell_write_file` returns `path`, `created`, `bytes`, `mode`, `old_sha256` (empty for a new file), `new_sha256`, `lines_old`, `lines_new`, `lines_delta` and `owner_preserved`; `shell_copy_path` returns `source`, `destination`, `created`, `bytes`, `mode`, `sha256` and `old_sha256`. Neither returns content. Both set the envelope's `verified: true`, which means the gate re-opened the file, re-read it and its SHA-256 equalled what was written. The gate answers a mismatch with `verify_failed`; a success whose `verified` is false is turned into `verify_failed` too, never a success with a warning. `expected_sha256` (64 lowercase hex digits) is passed through: the gate refuses the write with `exists` when the file's current content has another hash, and with `not_found` when the file does not exist.
- **Inputs.** `content` is required (an empty string writes an empty file) and, like `stdin`, is UTF-8 text of at most 1048576 bytes, checked by the server before anything is sent (the policy's `max_write_bytes` and `max_stdin_bytes` then apply on the gate). Modes are 3 or 4 octal digits; which bits are allowed (no setuid, setgid, sticky or world-write) is the gate's rule, so those modes reach the gate and are refused there with `policy_denied`. `action` is `start`, `stop`, `restart` or `reload`. `create` defaults to true; `parents` and `overwrite` to false. `timeout_seconds` is accepted by the tools that start a process on the target (`shell_control_service`, `shell_git_pull`, `shell_run_command`) and `max_output_bytes` by `shell_run_command`; the file tools use the server's default timeout.
- **Errors.** Gate refusals pass through with their code and message: `path_denied` (outside the write roots, deny list, protected set), `policy_denied` (unit, verb, repository, remote, dirty tree, non-fast-forward, mode bits), `not_authorized` (polkit), `exists`, `not_found`, `exec_failed`, `tier_denied`, `template_mismatch`.
- **Approval.** With the default `SHELL_MCP_APPROVAL_TIERS` (`destructive`) the operator tools run without approval, and giving them an `approval_id` is a `validation_error`. When the tiers list `operator`, every operator tool is approval-gated (section "Approval" above): with `SHELL_MCP_APPROVAL_METHOD=none` it refuses every call with `approval_unavailable`, whatever its arguments, and sends nothing to the target; otherwise the first call returns `approval_pending` after the preview below, and the re-call with `approval_id` runs the operation once.
- **Audit arguments.** `target`, plus `unit` and `action`; `path`, `mode`, `create`, `parents` and `content_bytes` (the size, never the content); `source`, `destination` and `overwrite`; `repo`; `command_id`, `args_count`, `cwd` and `stdin_bytes` (never argument values or stdin). `expected_sha256` is not logged. A gated call's line also carries `approval_id` and `approval_outcome` (`pending`, `used`, `invalid` or `declined`). The gate's and the helper's own audit lines record each request's `ceiling`.

**Approval previews (S4b-1b).** An approval-gated call's first request computes a preview from the gate's existing read operations, at the tool's ceiling; nothing that changes the host is sent. The preview, its SHA-256 and the gate's policy SHA-256 (from the preview responses' `gate` block) are bound to the approval record, and the re-call computes the preview again: a different hash is `approval_invalid` ("the target or policy changed since approval"). Previews hold only what does not change by itself between request and re-call: no memory figures, unit state timestamps or durations. A gate refusal while computing a preview (for example `path_denied`, or a file whose first bytes are a private key, which `read_file` refuses) is the call's result, and no approval is requested. Shapes, as the page shows them (keys flattened with `.` and `[i]`):

| Tool | Gate reads | Preview |
|---|---|---|
| `shell_write_file` | `stat`, then `read_file` for a regular file | `path`; `current`: `{state: absent}`, or `{state: file, size, mode, sha256, lines}`, or another type's stat (`{state: present, type, …}`); `new`: `{bytes, sha256, lines}`; `lines_delta`. `lines` and `lines_delta` are `null` unless the gate returned the whole file as unredacted text (its default read, up to 64 KiB). On the re-call, unless the caller gave `expected_sha256` (which is bound), the precondition is what the fresh preview saw: `expected_sha256` = `current.sha256` for a file, or the gate's `expect_absent` for `{state: absent}`, so the write is refused with `exists` if the content changes, or a file appears, after the fresh preview. An approval for a create never becomes a replace. (A file created before the re-call changes the fresh preview, which is `approval_invalid` first; `exists` is for one that appears between that preview and the write.) |
| `shell_copy_path`, `shell_move_path` | `stat` of the source, `stat` of the destination | `source`, `destination`: each `{state: absent}` or `{state: present, type, size, mode, uid, gid, owner?, group?, mtime, link_target?}`. |
| `shell_make_directory`, `shell_set_permissions` | `stat` | `path`: as above. |
| `shell_control_service` | `service_status` | `unit`, `load_state`, `active_state`, `sub_state`, `unit_file_state`, `main_pid`, `result`. |
| `shell_git_pull` | `git_status` | `repo`, `branch`, `head`, `upstream`, `ahead`, `behind`, `entries` (the first 50 porcelain records), `entries_total`, `truncated`. |
| `shell_delete_path` | `delete_preview` | `path`, `recursive`, `type`, `entries`, `bytes`, `first` (at most 50 entries) and `preview_sha256`. The hash covers every entry (path, type, size, device, inode, change and birth time), so any change to the tree, also beyond the first 50, changes the preview; the re-call passes the fresh preview's hash to the gate as `expected_preview_sha256`. |
| `shell_run_command` | `policy` | `command_id`, `tier`, `description`, `root_equivalent`, `template` (the first of the command's templates the arguments match), `args` (as given). Built from the policy only: no binary path, and path placeholders are shown as given, not resolved. An undeclared command (`policy_denied`), a command above the tool's ceiling (`tier_denied`) or arguments matching no template (`template_mismatch`) are refused here, as the gate would. The record's description is one line the server writes from the tool and the canonical arguments (for example "Write 12 bytes to /srv/app/config.yaml on app-host"). A path, unit or name appears in it only when it is plain (letters, digits and `._/@+=,:~-`, no spaces); otherwise the description says that it is shown in the arguments, where it is escaped data in a table. The canonical arguments are the typed input with defaults applied (`create: true`, the server's default `timeout_seconds` and `max_output_bytes`, `cwd` `/`, `args` `[]`), without `target` (bound separately, as resolved), `approval_id` and `confirm`.

## Destructive tier (profile = `admin`, policy `max_tier: destructive`, human approval)

| Tool | Gate op | Inputs | Preview shown in the approval request | Session |
|---|---|---|---|---|
| `shell_delete_path` | `delete` | `target`, `path`, `recursive=false` | `delete_preview`'s result. The re-call sends the fresh preview's `preview_sha256` as `expected_preview_sha256`, so the gate deletes exactly what that preview listed, or stops without deleting anything it did not list (POLICY §3); with `recursive`, refuses above `max_delete_entries`. | S4b-2a |
| `shell_discard_git_changes` | `git_discard` | `target`, `repo` | `git_discard_preview`. | S4b |
| `shell_run_command` (admin registration) | `exec` | as above | For `destructive` commands: the matched template and the resolved argv. | S4b-2b |

**Destructive tier: what the table leaves open (S4b-2a).** The read tier's rules on results, input forms, static schema maxima and the redaction order apply here too.
- **Registration and approval.** Destructive tools are registered only in the `admin` profile, with `readOnlyHint: false`, `destructiveHint: true`, `idempotentHint: false`, `openWorldHint: true`. They are approval-gated under every configuration, so they carry `_meta["anthropic/requiresUserInteraction"]: true` in every catalogue variant; under `SHELL_MCP_APPROVAL_METHOD=none` every call is `approval_unavailable` and nothing is sent to the target.
- **`shell_delete_path`.** The first call sends one `delete_preview` at ceiling `destructive` and returns `approval_pending`. The re-call sends `delete_preview` again (its hash must equal the approved preview's, else `approval_invalid` and nothing is deleted), then `delete` with `expected_preview_sha256` set to that fresh preview's `preview_sha256`, taken from the gate's answer before the server's redaction. `expected_preview_sha256` is not a tool input. The result is `path`, `type`, `entries`, `bytes` and `deleted: true`; a gate answer without `deleted` is `internal`, never a success.
- **Errors.** `exists`: the tree changed after the fresh preview, either before anything was deleted ("nothing was deleted") or during the deletion ("N of M entries were deleted and K were not"; preview the path again to see what remains). Nothing that was not in the preview is deleted in either case. `path_denied` (a root, outside the write roots, the deny list, the protected set and `.git`, a final symlink, a mount point, a device node), `bad_request` (a non-empty directory without `recursive`, or a filesystem without `RENAME_NOREPLACE`), `too_large` (`max_delete_entries`) and `not_found` pass through from the preview or the delete.
- **Descriptions.** "Delete `<path>` on `<target>`", with "and everything under it" for `recursive`; a path that is not plain is "a path shown in the arguments".
- **Audit arguments.** `target`, `path` and `recursive`; never the hash. The gate's audit line logs `path` and `recursive`, not `expected_preview_sha256`.

## Privileged tier (profile = `admin`; gate policy `privileged.enabled`; helper installed) — S4c

All run as root through the helper (`docs/PRIVILEGED.md`); paths, owners, modes, commands and packages are limited by the host's privileged policy. Annotations: read tools as the read tier; everything else `destructiveHint: true` because it changes root-owned state.

| Tool | Helper op | Inputs | Approval | Notes |
|---|---|---|---|---|
| `shell_priv_read_file` | `priv_read_file` | `target`, `path`, `offset`, `max_bytes`, `tail_lines?` | no | Root-only files within privileged read roots. |
| `shell_priv_list_directory` | `priv_list_dir` | `target`, `path`, `include_hidden`, `limit` | no | |
| `shell_priv_stat_path` | `priv_stat` | `target`, `path` | no | |
| `shell_priv_write_file` | `priv_write_file` | `target`, `path`, `content`, `owner?`, `group?`, `mode?`, `create=true`, `expected_sha256?` | **yes** — preview: line-count diff, old/new SHA-256, owner/mode | Backup first; read-back verified. |
| `shell_priv_make_directory` | `priv_mkdir` | `target`, `path`, `owner?`, `group?`, `mode?`, `parents=false` | **yes** | |
| `shell_priv_change_owner` | `priv_chown` | `target`, `path`, `owner?`, `group?`, `recursive=false` | **yes** — preview: entries affected | Owners from the allow-list only. |
| `shell_priv_set_permissions` | `priv_chmod` | `target`, `path`, `mode`, `recursive=false` | **yes** | Within the mode mask; never setuid/setgid/sticky. |
| `shell_priv_copy_path` / `shell_priv_move_path` | `priv_copy` / `priv_move` | `target`, `source`, `destination`, `overwrite=false` | **yes** | Overwritten destinations are backed up. Without `overwrite`, a destination that exists at the moment of the commit is refused with `exists`. |
| `shell_priv_list_backups` | `priv_list_backups` | `target`, `path?` | no | |
| `shell_priv_restore_backup` | `priv_restore_backup` | `target`, `backup_id` | **yes** — preview: diff against current | The current version is backed up first. |
| `shell_priv_delete_path` | `priv_delete` | `target`, `path`, `recursive=false` | **yes** — preview: entries and bytes | Destructive; backed up within `max_delete_entries`. |
| `shell_priv_run_command` | `priv_exec` | `target`, `command_id`, `args`, `cwd?`, `stdin?`, `timeout_seconds?` | **yes** for operator/destructive commands — preview: resolved argv, unit (core/broad) | Runs as root. |
| `shell_priv_update_package_index` | `priv_pkg_update_index` | `target` | **yes** | Broad unit. |
| `shell_priv_install_packages` | `priv_pkg_install` | `target`, `packages: list[str] (1..20)` | **yes** — preview: simulated transaction | Allow-listed names only. |
| `shell_priv_upgrade_packages` | `priv_pkg_upgrade` | `target` | **yes** — preview: simulated transaction | Only if the policy allows upgrades. |
| `shell_priv_remove_packages` | `priv_pkg_remove` | `target`, `packages` | **yes** — preview: simulated transaction | Destructive; allow-listed names only. |
| `shell_priv_reboot_host` | `priv_power` | `target`, `action` (`reboot` or `poweroff`) | **yes** — preview: the action and the unit systemd will start | Destructive; only actions the policy's `power` section allows; systemd starts `reboot.target` or `poweroff.target` (an orderly shutdown). |

The package tools' previews are the helper's read-tier `priv_pkg_install_preview`, `priv_pkg_upgrade_preview` and `priv_pkg_remove_preview` (`apt-get -s`); `priv_exec` for a broad-unit command carries `unit: broad` so the gate can route it (PRIVILEGED §6).

## Not in v1

A diagnostic tool, `shell_diag_elicit` (asks a harmless yes/no question through elicitation and reports what the client did), exists only in a binary built with the `shellmcp_diag` tag for local client testing; release builds and the image never contain it, and CI fails a cross-built binary that carries the tag.

Package managers other than apt, streaming/follow modes, file upload/download of binaries, archive extraction, container tools (use a container-manager MCP), anything in `docs/SECURITY.md` §4.

## Error contract

Every tool returns the envelope from `docs/ARCHITECTURE.md` §6. A non-zero process exit from `shell_run_*` is `ok: true` with `exec.exit_code` set; structured tools (`shell_git_pull`, `shell_control_service`) map a failed underlying command to `ok: false` with the gate's code and the exit status in `error.message`.
