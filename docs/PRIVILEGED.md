# Privileged helper (normative)

`shell-mcp-privd` is how shell-mcp performs actions that need root — without sudo, setuid, or a root shell. The gate stays unprivileged and sandboxed; when a request needs root it **asks** the helper over a local Unix socket, and the helper decides against its **own** root-owned policy, inside its **own** systemd sandbox.

This document is normative. The helper implements it exactly; changing it is a STOP-and-ask.

## 1. Why a helper instead of sudo

| | sudo from the gate | Privileged helper |
|---|---|---|
| Gate sandbox | Impossible: sudo needs setuid, which `no_new_privs` (required by Landlock) blocks. The gate would have to run unsandboxed. | The gate keeps `no_new_privs` + Landlock for every request. |
| How permission is expressed | sudoers rules that match argv text; wildcards match across arguments | Typed checks: "is this resolved path inside a declared root", "is this owner on the allow-list", "does this argv match a template" |
| What runs as root | Whatever command sudo starts — fully unconfined root | One small process, confined by systemd: only the capabilities it needs, writes only to declared paths, no network (core unit) |
| Who can call it | The service account, from any process it runs | Only the configured UID, verified by the kernel on the socket (`SO_PEERCRED`) |
| Non-TTY setup on the host | NOPASSWD rules for a service account | None — no sudoers file at all |

## 2. Components on each target

| Component | Owner / mode | Notes |
|---|---|---|
| `/usr/local/libexec/shell-mcp-privd` | `root:root 0755` | The helper binary (same Go module, third binary). |
| `/etc/shell-mcp/privileged.yaml` | `root:root 0600` | The privileged policy (§4). Only root reads it. |
| `shell-mcp-privd.socket` + `shell-mcp-privd@.service` | generated, `root:root 0644` in `/etc/systemd/system/` | **Core** unit: tight sandbox, no network (§5.1). |
| `shell-mcp-privd-broad.socket` + `shell-mcp-privd-broad@.service` | generated, same | **Broad** unit: for package management, commands declared `unit: broad` and the power operation (§5.2). Generated and installed only when the policy uses it (`packages.enabled`, a `unit: broad` command, or `power`). |
| Socket group (placeholder name `svc-shell-priv`) | system group | The gate's service account is its only member; sockets are `root:<group> 0660`. |
| `/run/shell-mcp/` | `root:root 0711` | Created by systemd for the socket (`DirectoryMode=0711`). `SocketUser=`/`SocketGroup=` apply to the socket node only, so the directory stays root's; the gate needs only search permission to reach the socket by name, not to list the directory. |
| `/var/lib/shell-mcp/backups/` | `root:root 0700` | Previous versions of files the helper overwrites or deletes (§6). Created at install; the core unit lists it in `ReadWritePaths=` and does not start without it. |

Units are **generated** from the policy by `shell-mcp-privd units --policy /etc/shell-mcp/privileged.yaml` and embed the policy's SHA-256 (`Environment=SHELL_MCP_PRIVD_POLICY_SHA256=…`), its `client_uid` (`Environment=SHELL_MCP_PRIVD_CLIENT_UID=…`, so the peer check reads nothing from disk, §7) and which unit they are (`Environment=SHELL_MCP_PRIVD_UNIT=core` or `…=broad`). Each instance knows its unit and refuses an operation meant for the other one (`helper_wrong_unit`, §6), so the helper, not the gate, is authoritative for routing. The helper refuses to serve if the policy on disk no longer matches, so a policy edit without regenerating the units (whose `ReadWritePaths=` came from the old policy) fails closed; it tells the gate so (`helper_policy_mismatch`).

Sockets use `Accept=yes`: systemd starts one short-lived helper instance per connection, which serves exactly one request and exits. There is no long-running root daemon.

## 3. Trust and authentication

1. The gate connects to `/run/shell-mcp/privd.sock` (or `privd-broad.sock`). File permissions (`0660`, group-owned) are the first gate.
2. The helper reads `SO_PEERCRED` on the accepted socket and requires the uid to equal the unit's `SHELL_MCP_PRIVD_CLIENT_UID` (generated from the policy's `client_uid`; once the peer has passed, the policy's value must equal it too, §7). Anything else: close without a response and audit-log it. This is the first thing the helper does (§7).
3. One request per connection, same wire format as the gate protocol v1 (ARCHITECTURE §4), ops prefixed `priv_`. Request ≤ 2 MiB, response ≤ 4 MiB, strict decoding (unknown fields and duplicate keys are errors).
4. The helper **never trusts the gate**: it re-validates tier, paths, owners, modes, templates and sizes against its own policy. The gate's policy and the helper's policy are independent; both must allow an operation. The request's `ceiling` (ARCHITECTURE §4.1), forwarded by the gate unchanged, is applied by the helper itself as well (§6). Its `timeout_ms` is the timeout the gate waits for (the request's, clamped to the gate policy's limits), and the helper clamps it again to its own `limits.max_timeout_s` (§6).
5. Every response carries the helper's own block: its version, the privileged policy's SHA-256, its `max_tier` and its `unit` (`core` or `broad`). The gate passes it to the server unchanged as the response's `helper` block (ARCHITECTURE §4.2), and the server binds the privileged policy's hash into the approval of every privileged operation (D-006), so an edit of this policy between an approval and its re-call is `approval_invalid`.

**What approval does and does not cover.** Human approval (D-006) is enforced by the MCP server, which holds the approval records and verifies the approver's code. It stops a prompt-injected model from acting without the user. It cannot stop a **fully compromised server**, which could skip the prompt — that case is bounded by the gate policy, the privileged policy and the helper's sandbox. Write the privileged policy for that worst case.

## 4. Privileged policy schema

```yaml
version: 1
client_uid: 60123               # example — the gate service account's pinned UID (D-020); required; never 0
socket_group: svc-shell-priv    # must exist locally; must not be in the D-020 deny list or gid 0
max_tier: operator              # read | operator | destructive
sandbox:
  landlock: required            # required (default) | best-effort — as in the gate policy (§7)
limits:
  max_read_bytes: 1048576
  max_write_bytes: 1048576
  max_output_bytes: 1048576
  default_timeout_s: 60
  max_timeout_s: 900            # package operations can be slow; hard ceiling 1800
  max_delete_entries: 1000
paths:
  read:  [/etc/example-app, /var/log/example-app]      # root-readable roots
  write: [/etc/example-app]                            # root-writable roots (implicitly readable)
  persistence:                                          # write roots inside normally-protected persistence areas
    - path: /etc/systemd/system/example-app.service.d
      acknowledge: "drop-ins for example-app only"      # required non-empty justification; flagged by check-policy
  deny: ["/etc/example-app/secrets/**"]
owners:                          # the only users/groups chown/chgrp may set
  users: [root, example-app]
  groups: [root, example-app]
modes:
  max: "0755"                    # no bits outside this mask; setuid/setgid/sticky never allowed
backups:
  keep: 10                       # per file; 0 disables backups (not recommended)
  max_store_bytes: 1073741824    # the whole store, data and metadata (64 MiB..1 TiB; default 1 GiB)
commands:                        # run as root, templates exactly as POLICY.md §4
  - id: nginx-test
    path: /usr/sbin/nginx
    tier: read
    templates: [["-t"]]
  - id: renew-certs
    path: /usr/local/bin/example-renew
    tier: operator
    unit: broad                  # needs network → runs under the broad unit; core is the default
    root_equivalent: false
    templates: [["--all"]]
  - id: firewall-list
    path: /usr/sbin/nft          # a normally hard-denied binary (§5.3 list B)
    tier: read
    acknowledge: "firewall rules are listed, never changed"
    templates: [["list", "ruleset"]]
power:                           # the built-in priv_power operation (§6); omitted = not allowed
  allowed: [reboot]              # reboot | poweroff
  acknowledge: "planned maintenance windows only"   # required, one line (list B, POLICY §5 group 11)
packages:
  enabled: false
  manager: apt                   # only apt in v1
  install: [htop, jq]            # exact package names allowed for install
  remove: [htop]                 # exact package names allowed for removal
  allow_update_index: true       # apt-get update
  allow_upgrade: false           # apt-get upgrade of everything installed
```

`examples/privileged/privileged.yaml` is a complete, commented example with placeholders; a test loads it and generates both unit pairs from it.

Rules:
- Strict parsing, as the gate policy. Roots absolute and already clean; not `/`, `/proc`, `/sys`, `/dev`, `/run`. A root may appear under both `paths.read` and `paths.write` (write roots are readable anyway).
- `paths.write` and `paths.persistence` may not be, be inside, or contain a path on the **never** set (§5.3), nor be inside a `.git` directory; `paths.read` may not be or be inside a never-set path (a read root such as `/etc` may contain them: the deny list and the unit's `InaccessiblePaths=` keep credentials out). Paths in the gate's normal protected set (POLICY §3) that are *not* in the never set — systemd unit directories, cron directories, `/etc/profile.d`, `/usr/local/sbin`, … — may only appear under `paths.persistence` with an `acknowledge` string (one line). `/usr/local/bin` holds the gate binary, so it is never a write root.
- Commands resolve and ownership-check exactly as the gate's (root-owned binary and parents, not group/other-writable, binary identity check), with the same placeholder rules (no leading `-`, typed placeholders, `{path:read}`/`{path:write}` resolved against *this* policy's roots; `{unit}` is not available). A command may carry a one-line `description`. POLICY §5 groups 1–10 are refused by name (as written and resolved) and by identity; groups 11–13 need a non-empty `acknowledge`. `systemctl`, `journalctl`, `git` and this project's own binaries may not be commands.
- `unit:` is `core` (default) or `broad`. `capabilities:` may add only the capabilities below, each valid only where it has an effect; every addition is reflected in the generated unit and reported by `check-policy`:

  | Capability | Core unit | Broad unit |
  |---|---|---|
  | `CAP_SYS_BOOT` | yes (the unit then keeps `@reboot` in its syscall filter) | yes (already in its full set) |
  | `CAP_KILL` | yes (the unit then uses `ProtectProc=default`, §5.1, and Landlock leaves signals unscoped) | yes (already in its full set) |
  | `CAP_SYS_ADMIN` | yes, with `root_equivalent: true` | yes, with `root_equivalent: true` |
  | `CAP_SYS_TIME` | no — `ProtectClock=yes` removes it from the bounding set and filters `@clock` | yes — the broad unit then drops `ProtectClock=yes` (§5.2) |
  | `CAP_NET_ADMIN`, `CAP_NET_BIND_SERVICE` | no — the core unit has a private network namespace and only `AF_UNIX` sockets | yes (already in its full set) |

  Capabilities of broad-unit commands never reach the core unit's bounding set.
- `modes.max` is 3–4 octal digits without setuid, setgid, sticky or world-write bits (default `0755`). A requested mode outside it is refused (`policy_denied`). **Every inode the helper creates gets a mode within it:** a new file (default `0640`), a directory (default `0750`), a copy (the source's mode), a file written or copied over an existing one (the existing file's mode), and a restored file or tree entry (the recorded mode), each without setuid, setgid, sticky and world-write and masked by `modes.max`. So **a file whose mode is wider than `modes.max` is narrowed to the mask when the helper writes it, copies over it or restores it** (for example, under `modes.max: "0700"`, an existing `0640` file is written as `0600`). `backups.keep` is 0..100 (default 10). `backups.max_store_bytes` is 67108864 (64 MiB, one backup's maximum) to 1099511627776 (1 TiB), default 1073741824 (1 GiB): the total bytes of every file in the backup store, data and metadata together; validated also when `keep` is 0, when it is not used. `check-policy` reports it with the store's current use (§6, Backups). Limit ceilings: `max_read_bytes` and `max_output_bytes` ≤ 4 MiB, `max_write_bytes` ≤ 1 MiB, `max_timeout_s` ≤ 1800, `max_delete_entries` ≤ 10000.
- `unit: broad`, `packages` and `power` need the broad unit; `unit: broad` and `packages` are **root-equivalent** (a package's maintainer scripts run arbitrary code as root). All three are always reported by `check-policy`.
- `packages`: `manager` is `apt` (default); `install` and `remove` hold at most 256 exact Debian package names each (Debian Policy §5.6.1: lower-case letters, digits, `+`, `-`, `.`, at least two characters, alphanumeric first, at most 128 bytes), without duplicates. An `install` name may not end in `-` and a `remove` name may not end in `+`: apt-get reads those suffixes as "remove" and "install" when no package has that exact name, which would turn one operation into the other. With `enabled: true`, `/usr/bin/apt-get` must resolve to a root-owned, not group/other-writable executable.
- `power`: `allowed` lists `reboot`, `poweroff` or both, without duplicates; `acknowledge` is a required one-line justification. A policy whose `max_tier` is below `destructive` gets a warning (priv_power is destructive).

## 5. Sandboxes

### 5.1 Core unit (generated)

`User=root`, `NoNewPrivileges=yes`, `CapabilityBoundingSet=CAP_CHOWN CAP_FOWNER CAP_DAC_OVERRIDE CAP_DAC_READ_SEARCH` (+ declared `capabilities`), `ProtectSystem=strict`, `ReadWritePaths=<paths.write> <paths.persistence> /var/lib/shell-mcp/backups`, `InaccessiblePaths=` the never-readable credential paths (`-/etc/shadow -/etc/shadow- -/etc/gshadow -/etc/gshadow- -/etc/sudoers -/etc/sudoers.d -/etc/security/opasswd -/etc/ssh -/root/.ssh`; the directive takes no globs, and `-` ignores a path this host lacks), `ProtectHome=read-only`, `TemporaryFileSystem=/run:ro`, `ProtectProc=ptraceable` (`default` when a core-unit command declares `CAP_KILL`), `ProcSubset=pid`, `PrivateTmp=yes`, `PrivateDevices=yes`, `PrivateNetwork=yes`, `RestrictAddressFamilies=AF_UNIX`, `IPAddressDeny=any`, `ProtectKernelTunables=yes`, `ProtectKernelModules=yes`, `ProtectKernelLogs=yes`, `ProtectControlGroups=yes`, `ProtectClock=yes`, `ProtectHostname=yes`, `RestrictNamespaces=yes`, `RestrictRealtime=yes`, `RestrictSUIDSGID=yes`, `LockPersonality=yes`, `MemoryDenyWriteExecute=yes`, `SystemCallArchitectures=native`, `SystemCallFilter=@system-service` minus `@mount @module @reboot @swap @raw-io @debug @obsolete` (adjusted only for declared capabilities: `CAP_SYS_BOOT` keeps `@reboot`), `UMask=0077`, `RuntimeMaxSec=<max_timeout_s + 30>`, `TasksMax=64`, `MemoryMax=256M`, `KillMode=control-group`, `TimeoutStopSec=5`. The generated service also carries what running it needs — `ExecStart=`, `StandardInput=socket`, `StandardOutput=socket`, `StandardError=journal`, `SyslogIdentifier=shell-mcp-privd`, `Environment=SHELL_MCP_PRIVD_POLICY_SHA256=<hash>`, `Environment=SHELL_MCP_PRIVD_CLIENT_UID=<client_uid>` (never 0 or 4294967295), `Environment=SHELL_MCP_PRIVD_UNIT=core`, and `CollectMode=inactive-or-failed` so finished instances do not accumulate — and the socket `ListenStream=/run/shell-mcp/privd.sock`, `Accept=yes`, `SocketUser=root`, `SocketGroup=<socket_group>`, `SocketMode=0660`, `DirectoryMode=0711`, `MaxConnections=16`. A path or name that a unit file would reinterpret (whitespace, quotes, `\`, `%`, `$`, a component starting with `-`) makes `units` refuse rather than quote it. Inside that, the helper also applies Landlock from its policy before reading the request: read+execute on `/usr /bin /sbin /lib /lib64` and each command's binary; read on the read roots, `/etc/passwd`, `/etc/group`, `/etc/ld.so.cache` and its own `/proc/<pid>`; read+write (no execute) on the write and persistence roots and the backup store; `/dev/null`, `/dev/urandom`; no socket and no TCP rule, so from ABI 4 every TCP bind and connect is denied; from ABI 8 signals and abstract Unix sockets are scoped to the helper's own domain, except that signals are left unscoped when a core-unit command declares `CAP_KILL` (otherwise the capability could reach no process outside the helper). The helper starts every command by re-executing its own binary (the exec trampoline, ARCHITECTURE §2, `internal/gate/execx`), so that binary must sit under one of those read+execute directories, as `/usr/local/libexec/shell-mcp-privd` does; `check-policy` warns otherwise. (Every directive was verified against `systemd.exec(5)`, `systemd.socket(5)` and `systemd.resource-control(5)` for systemd 257 and 259; see ARCHIVE §14, S1c and S1d, with the `systemd-analyze security` score.)

Why these directives, and why not others:

- **`/run` is an empty read-only tmpfs.** `/run` holds the system bus socket, systemd's private socket, and the sockets of other root services (a container engine's, for example). Below Landlock ABI 9, which governs pathname Unix-socket connects, root can connect to any socket file it can reach, and each of those is root-equivalent for a root client — the system bus alone lets root have PID 1 start any unit, outside every sandbox. `TemporaryFileSystem=/run:ro` hides all of them; `/var/run` is the usual symlink to `/run`, so it points into the same empty tmpfs (`units` and `check-policy` refuse a host where `/var/run` is anything else). The helper needs nothing under `/run`: its connection and its journal stream are file descriptors set up before the namespace. (`InaccessiblePaths=/run` would not work on systemd 257: after setting up the namespace it remounts its own `/run/systemd/incoming`, which an inaccessible `/run` removes, so the unit would fail to start. A tmpfs lets systemd create that mount point.) **Abstract Unix sockets** are not files; they belong to a network namespace, and `PrivateNetwork=yes` gives the core unit its own ("`AF_UNIX` sockets in the abstract socket namespace of the host will become unavailable", `systemd.exec(5)`, 257 and 259). So the core unit reaches no local IPC endpoint of the host at all; Landlock's abstract-socket scope (ABI 8) adds the same inside it.
- **`ProtectProc=ptraceable`, `ProcSubset=pid`.** The core unit's `/proc` shows only processes it may ptrace, and only process directories. Two rules decide which processes those are, and the core unit fails both for everything outside itself:
  - It has no `CAP_SYS_PTRACE`, so every other user's process is hidden.
  - Under Landlock (§5.1 above) a process may not access, in any ptrace mode (procfs's read mode included), a process outside its own Landlock domain (`hook_ptrace_access_check()`, `security/landlock/task.c`). So root-owned processes are hidden too, although the uids match: core-unit commands see only the helper instance and its own children.

  When a core-unit command declares `CAP_KILL`, the unit uses `ProtectProc=default` instead, because signalling a process requires finding it first; every process is then visible. Where Landlock is not applied (`sandbox.landlock: best-effort` on a kernel without it), root-owned processes stay visible under `ptraceable`, because the ptrace check passes on a matching uid.
  - **Why not `invisible`.** With `hidepid=invisible` the kernel exempts members of procfs's `gid=` group before the ptrace check (`has_pid_permissions()`, `fs/proc/base.c`). systemd passes no `gid=`, so that group is gid 0 (`fs_info` is zero-allocated, `fs/proc/root.c`), and the helper runs as root:root, so `invisible` would hide nothing. The runner showed exactly that. `hidepid=ptraceable` skips the group exemption and applies the ptrace check alone.
  - **Other processes' environments stay out of reach, even when processes are visible** (`ProtectProc=default`). The core unit's Landlock ruleset grants nothing in `/proc` except the helper's own `/proc/<pid>` (§5.1 above), so a declared command cannot open another process's `environ`, or anything else under its `/proc/<pid>`. And `priv_read_file` refuses every `/proc` path, because no root may be `/proc` or inside it (§4). As defence in depth behind both rules, `/proc/*/environ`, `/proc/*/mem`, their per-thread forms `/proc/*/task/*/environ` and `/proc/*/task/*/mem`, and `/proc/kcore` are also on the built-in read deny list (POLICY §3), which refuses them on its own. The e2e proves this against a root process carrying a canary variable: hidden (`ENOENT`) under `ptraceable`, and refused by Landlock (`EACCES`) under `default`.
- **Never `PrivateUsers=`, `RootDirectory=` or `RootImage=`.** A private user namespace maps the host's users away, so `chown` to an owner from `owners` could not work; a separate root filesystem defeats working on the host's own files. The generator refuses to emit them.

### 5.2 Broad unit (generated, only when used)

For `packages`, commands declared `unit: broad` and `power`; generated only when the policy uses one of them. Network allowed, `ProtectSystem=` off (package managers write `/usr`, `/etc`, `/var`), full root capabilities. Still: `NoNewPrivileges=yes`, `PrivateTmp=yes`, `ProtectKernelModules=yes`, `ProtectKernelTunables=yes`, `ProtectClock=yes`, `RestrictSUIDSGID=` off (packages ship setuid binaries), `RuntimeMaxSec`, `TasksMax`, `MemoryMax`, `KillMode=control-group`, `TimeoutStopSec=5`. Package operations run apt-get with `DEBIAN_FRONTEND=noninteractive` and `-o Dpkg::Options::=--force-confold` (existing config files are never overwritten by package upgrades). Every broad operation that changes something is approval-gated, and everything the broad unit serves is audit-logged at WARN.

The generated service is exactly: `ExecStart=`, `StandardInput=socket`, `StandardOutput=socket`, `StandardError=journal`, `SyslogIdentifier=shell-mcp-privd`, the same `SHELL_MCP_PRIVD_POLICY_SHA256` and `SHELL_MCP_PRIVD_CLIENT_UID` lines as the core unit, `Environment=SHELL_MCP_PRIVD_UNIT=broad`, `User=root`, `NoNewPrivileges=yes`, `PrivateTmp=yes`, `ProtectKernelModules=yes`, `ProtectKernelTunables=yes`, `ProtectClock=yes`, `RuntimeMaxSec=<max_timeout_s + 30>`, `TasksMax=256`, `MemoryMax=1G` (apt-get and dpkg with maintainer scripts need more than one core-unit request), `KillMode=control-group`, `TimeoutStopSec=5`, and `CollectMode=inactive-or-failed`; nothing for the network, `ProtectSystem=`, the capability bounding set or `RestrictSUIDSGID=`, which are therefore off. The socket is the core unit's with `ListenStream=/run/shell-mcp/privd-broad.sock`. There is no Landlock sandbox in the broad unit. There is no `User=` either: the service runs as root without it, and with `User=` systemd drops `CAP_SETUID` from a unit that has seccomp filters (its `keep_seccomp_privileges` path in `exec-invoke.c`, systemd 257 and 259; `ProtectClock=` and `ProtectKernelModules=` install filters), which apt needs to switch to its `_apt` user (seen on the runner: `seteuid 42 failed`).

**`CAP_SYS_TIME` relaxes `ProtectClock=`.** `ProtectClock=yes` removes `CAP_SYS_TIME` and `CAP_WAKE_ALARM` from the bounding set and filters the clock-setting system calls, so a broad command that declares `CAP_SYS_TIME` could not use it. When one does, the broad unit is generated without `ProtectClock=`; that is the only directive a capability may relax, in either unit, and the core unit keeps it.

**Self-check.** The broad instance's bounding set may be at most root's full set without `CAP_SYS_MODULE` (dropped by `ProtectKernelModules=yes`) and, while it keeps `ProtectClock=yes`, without `CAP_SYS_TIME` and `CAP_WAKE_ALARM`; anything broader is `helper_capabilities_broad`.

**What `ProtectKernelModules=`, `ProtectKernelTunables=` and `ProtectClock=` cost.** A package whose maintainer scripts load kernel modules, write `/proc/sys` or `/sys`, or set the clock fails inside the broad unit; so does installing into `/usr/lib/modules`, which `ProtectKernelModules=` hides. Kernel and kernel-module packages are therefore not installable through the helper in v1. (`ProtectClock=` would add a read-only rule for the RTC devices only where a device policy is already in force; the broad unit has none, so it keeps access to every device — systemd 257 and 259, `unit_patch_contexts()`.)

**When an instance stops or dies (both units).** The helper starts each command with `Pdeathsig=SIGKILL`, so its death kills the command at once. That covers the command alone: the kernel clears the signal when the command changes its user, group or filesystem ids (apt-get switching to `_apt`, any root command that drops privileges; `commit_creds`), and the command's own children never had one. Both units therefore set `KillMode=control-group` (systemd's default, written explicitly) and `TimeoutStopSec=5`: when an instance stops, including after its helper died, systemd sends `SIGTERM` to everything left in its cgroup and `SIGKILL` 5 s later (`systemd.kill(5)`, `systemd.service(5)`, systemd 257 and 259). The helper installs no `SIGTERM` handler and exits at once, so the bound only ever applies to leftovers. A core-unit command cannot switch user at all (no `CAP_SETUID` or `CAP_SETGID` in its bounding set); a broad-unit command can.

### 5.3 What the helper will never do

**List A — never, in any policy** (the helper refuses to load a policy that tries):
- Identity and access: users, groups, passwords (`/etc/passwd`, `/etc/group`, `/etc/shadow*`, `/etc/gshadow*`), sudoers, PAM (`/etc/pam.d`, `/etc/security`), SSH server config and keys (`/etc/ssh`), any `authorized_keys`, polkit rules (`/etc/polkit-1`, `/usr/share/polkit-1`).
- This project's trust anchors: `/etc/shell-mcp`, the gate and helper binaries, the helper's units, `/run/shell-mcp`.
- Credential reads: shadow files, private keys (the built-in read deny list of POLICY §3 applies here too, plus private-key content sniffing).
- Commands from POLICY §5 groups 1–10 (shells, interpreters, launchers, debuggers, pagers/editors, privilege changers, tunnels, session tools, identity and scheduling administration); setuid/setgid/sticky bits.

**List B — declarable only with `acknowledge` (and capabilities where needed):** POLICY §5 groups 11–13 (power, kernel and storage, firewall), the built-in power operation (the `power` section, §4), and writes to persistence areas (systemd unit directories, cron directories, `/etc/profile.d`, `/usr/local/bin`, `/usr/local/sbin`, `/etc/ld.so.conf.d`). These are legitimate administration and also the easiest ways to lose or own a host; `check-policy` lists every one.

## 6. Operations

| Op | Tier | Approval | Notes |
|---|---|---|---|
| `priv_read_file`, `priv_list_dir`, `priv_stat` | read | no | Within privileged read/write roots; deny list and private-key sniffing apply. `priv_read_file` returns a file under a directory another account could write only when that account could read it itself ("Files another account could have moved in", below). |
| `priv_backup_check` | read | no | `{path}` → `{written, bytes, fits, store_bytes, max_store_bytes}`: whether an overwrite of `path` now would write a backup (a regular file there and `backups.keep` above 0), of how many bytes, and whether it fits the store's cap, counted exactly as the backup would count it (Backups below), with the store's current use and cap. The path must be one the write operations may change (a write root, not denied or protected), so the server's composed previews (S4c-2) learn that too; a store that cannot be counted is `backup_failed`. Changes nothing. Added to protocol v1 in place, before any release (handoff P-11). |

**Tier and ceiling.** Each request carries a required `ceiling` (`read`, `operator` or `destructive`: the tier of the server tool that made it, ARCHITECTURE §4.1), which the gate forwards unchanged. A request without one, or with another value, is `bad_request`. Once the operation is known to belong to this unit (for `priv_exec`, once the command is known to be declared and to belong to it), the helper refuses with `tier_denied`, before anything else, any operation in the table above, and any `priv_exec` command, whose tier is above **min(`max_tier`, `ceiling`)**; the message names the limit that applied. The gate applies min(`privileged.max_tier`, `ceiling`) to the operation's fixed tier before it connects, but it cannot know a command's tier, so for `priv_exec` the helper's check is the one that counts. The ceiling only lowers the limit. It is defence in depth against server mistakes and races, not against a compromised server, which can send any ceiling: this policy remains the boundary for that, so write it for the worst case (§3).

**Package operations** run `/usr/bin/apt-get` with a fixed argv — `-q -y -o Dpkg::Options::=--force-confold -o Dpkg::Use-Pty=0 -o APT::Get::AutomaticRemove=false`, then `--no-install-recommends` (install, upgrade) or `-o APT::Get::Purge=false` (remove), `-s` for a preview, the command, and package names only after `--`, which ends apt-get's option parsing (verified in apt 3.0.3 and 3.1.16) — and the fixed command environment plus `DEBIAN_FRONTEND=noninteractive`. There is never a free-form apt argument. When apt-get fails because another process holds the dpkg frontend, administration or package-list lock, it is run again every 2 s for at most `min(60 s, timeout / 2)` (apt refuses before changing anything when it cannot lock); after that the operation is `exec_failed` saying the package database is locked. Otherwise a failed transaction is data: `ok: true` with the exit code and the capped, redacted stdout and stderr.

**Routing.** The core unit's instance serves the file operations, backups and core commands; the broad unit's serves the package operations, their previews, `priv_power` and broad commands. The gate sends each op to `privileged.socket` or `privileged.broad_socket` accordingly (ARCHITECTURE §3), but each instance checks, before anything else about the request, that the operation belongs to its unit, and refuses it otherwise with `helper_wrong_unit` — never executed, whatever the gate sent where.

Every write-class op has a preview, shown in the approval request: no op returns one itself; the preview is a separate read op, or composed by the server from read ops (the diff summary for writes, the resolved argv for exec, the simulated transaction for package operations; `docs/handoff/S4C-PRIVILEGED.md` D2 says which, per op).

**Timeouts.** The helper runs an operation for at most the request's `timeout_ms` (absent or 0: `limits.default_timeout_s`), clamped to `limits.max_timeout_s`; a command or apt-get still running then gets `SIGTERM` and, 2 s later, `SIGKILL` on its process group, and the answer (`timed_out`) comes only after it has ended. The gate forwards as `timeout_ms` the timeout it waits for itself, and waits 15 s longer for the answer (ARCHITECTURE §3 step 4), so in the normal case the gate's answer is the helper's, after the command has ended. Only an instance that takes more than those 15 s to start, or to end its command, lets the gate answer `timeout` first (`docs/handoff/S4C-PRIVILEGED.md` X-4; the message for that case is S4c-6's and S4c-7's).

**Redaction.** The helper redacts what it returns (file content, command output) with the built-in rules only: the privileged policy has no redaction patterns. The server then applies its own built-in rules and `SHELL_MCP_REDACT_PATTERNS` (TOOLS.md).

**Backups.** Before any overwrite (write, copy or move over a file), delete or restore, the helper copies what would be lost into `/var/lib/shell-mcp/backups/` through the same verified descriptors the operation uses: for a file, `<id>.data` (its bytes); for a directory tree, `<id>.tar` (its directories and regular files with their modes, owners and modification times, written from the delete's plan; a tree holding a symlink or special file cannot be backed up, so it is not deleted). Beside it, `<id>.meta.json` records the backup id (`YYYYMMDDTHHMMSSZ-<16 hex>`), kind, original path, owner, group, mode, size, SHA-256, time, op and request id. Both are `root:root 0600`, written under temporary names, fsynced and renamed data first, so a backup exists exactly when its metadata does. `backups.keep` versions are kept per original path; older ones are removed only once the operation that made the new backup has succeeded, and a request's own backups are never removed by its retention (an operation that fails after its backup keeps every older version too). **A failed operation's backup is kept unless the operation is provably unchanged.** fsx marks a refusal as unchanged only where it made no mutating system call of the operation, or undid the one it made: the file changed between its hash and its backup (or between the backup and the commit), a create-only commit refused by `link(2)` or `RENAME_NOREPLACE`, and a verified replace that was exchanged back or never exchanged. Only then, and only if fsx reported no commit for the request, does the helper delete the backups the request wrote (metadata first, under the store lock), so such failures cannot fill the store; the audit line moves their ids from `backup_ids` to `backup_ids_discarded`, so the journal shows they were written and removed. Every other failure, an unknown state included (a read-back mismatch, an I/O error, a mutating site that does not report), keeps its backups: they may hold the previous version of a file that did change. A delete is provably unchanged only when its own accounting shows it unlinked nothing, stranded nothing and put back every entry it set aside ("Delete", below). A backup larger than 64 MiB, a missing or group/other-accessible store, or any write error is `backup_failed`, and the operation changes nothing.

**The store's size cap (`backups.max_store_bytes`).** The bytes of every file in the store, data and metadata together, stray files included, may not exceed the cap. Before each backup, under an exclusive lock on the store directory (one backup at a time across helper instances, waited for up to 10 s), the helper counts the store as it will be afterwards: this backup added, and the versions of the same path that this backup's own retention will remove once its operation succeeds taken away, so a file rewritten again and again at `backups.keep` versions never trips it. A backup that would exceed the cap is refused with `backup_failed`, "the backup store is full (N of M bytes used); nothing was changed; remove old backups on the host or raise backups.max_store_bytes", and the operation changes nothing; the data written is also bounded by the room left. A store whose total cannot be counted (more than 20000 names, an entry that is not a regular file, a metadata file that does not decode) refuses every backup the same way (fail closed). `priv_backup_check` answers the same question without writing anything, so a preview can refuse before an approval is requested.

**Backups bound to what was approved.** fsx hashes the file it is about to replace through a verified descriptor and hands that hash to the backup; the file backed up must be that version (same inode, size and mtime) or the backup is refused before it is written, and its bytes must have that hash and the request's precondition hash (`expected_sha256` of a write, `expected_destination_sha256` of a copy or move), or the backup is refused (`backup_failed`, nothing changed). The metadata records that precondition hash as `preview_sha256` (a local file format; `v` stays 1, and older metadata without it still decodes).

**Verified replaces.** Linux has no conditional rename-over, so every commit that replaces an existing file (a write, a copy or a move over one) is a `renameat2(2)` `RENAME_EXCHANGE` of the new file and the destination, followed by a check that the inode exchanged out is the one that was checked and backed up (same inode, size and mtime). Anything else (a file renamed over the destination, or one rewritten in place, after the last check) is exchanged back and the operation refused with `exists`, nothing replaced; only then is the old inode's name removed. A filesystem without `RENAME_EXCHANGE` (for example NFS) is refused with `bad_request`, never replaced unchecked. What remains is POLICY §3's third case for a delete: a process that already holds the old file open for writing and writes through that descriptor after the check writes into an inode that is then removed; and a process with write access to the directory could swap the exchanged-out name in the moment before its check (it could replace the destination itself). And the check compares inode, size and mtime, never the change time: the exchange itself changes the ctime of both inodes it renames (rename updates an inode's ctime), so a ctime taken before it can never match after it. So the destination's owner (or anyone who may write it and set its times) could edit it in place, keep its size, and reset its mtime to the old value with `utimensat(2)` at the exact moment between the last check and the exchange; that edit is then overwritten, and the backup holds the content as hashed before the edit. Mtime comparisons are also only as fine as the kernel's timestamps, so a same-size rewrite within one clock tick is the same case without the reset. Every privileged write root's filesystem is probed for `RENAME_EXCHANGE` by `check-policy` (and for `RENAME_NOREPLACE`, which moves without overwrite need), with a WARN naming the root and the missing flag. A file replaced or rewritten while it was being backed up is not destroyed, and a recursive delete stops before removing any entry the backup did not see. `priv_list_backups` lists metadata (newest first, filtered by path); `priv_restore_backup` restores a file (with its recorded owner and its recorded mode within `modes.max`, backing up the current version first) or a tree (only where nothing exists now), after checking the data's SHA-256 ("Restore", below).

**Chown and chmod.** They change existing inodes in place, as root, so they must change exactly the inodes the approver saw, and only inodes nobody else could have put under the write root (handoff D4, F-2, N-1).
- **The walk** (the preview and the operation alike) is the delete's: each directory opened as an `os.Root` from its parent's handle and re-checked by requested and real path and by `statx` identity, never following a symlink and never entering another mount. It refuses (and the preview requests no approval): a root of the policy and a tree holding one; anything outside the write roots, denied or protected; a final symlink; a mount point and a tree holding one; device nodes, FIFOs and sockets in a tree (a special file as the target is `bad_request`); `.shell-mcp-delete-*` names; setuid, setgid and sticky files and directories (`policy_denied`); a non-directory with more than one link, anywhere in the walk (`path_denied`, naming the path and the count: its other name can lie outside the write roots, and roots, `ReadWritePaths=` and Landlock confine paths, not inodes; Landlock has no chmod or chown right); more than `limits.max_delete_entries` entries (`too_large`). Symlinks inside a tree are listed, never followed and never changed (no `lchown`).
- **Another account cannot have put it there (the chain rule).** An account that can write a directory under a write root and the directory of a file elsewhere on the same filesystem could move that file in, have it changed, and move it out again; the link count stays 1. So an entry is changed only when every directory from `/` to it is root's and neither group- nor world-writable (the group bits are the ACL mask, an upper bound on every named ACL entry): then only root can have put it there. The directories from `/` to the target's parent are checked by descriptor, each opened from the previous one (`O_PATH|O_NOFOLLOW`, never a separate lookup of a path), and the last must be the parent the operation holds; inside a tree, every directory that holds entries is checked as the walk opens it. A failure is `path_denied` naming the directory and its owner or mode. **Consequence:** everything under a directory that an application account owns or can write is refused (an application-owned data directory, a `2775` shared directory); the directory itself can still be changed, since its own path is root's. In particular, **once a tree has been chowned to an application account, every later `priv_chown` or `priv_chmod` inside it is refused, a second `recursive` chown of the same tree included**: its directories are now that account's, so that account could have moved anything in. This is deliberate. The intended way to manage application-owned trees is a fixed root command template in this policy's `commands` (`priv_exec`, `shell_priv_run_command`, S4c-6): the operator writes it, it is template-matched like every command, and running it still needs approval. `check-policy` prints `ok` or a WARN for each privileged write root whose own path fails the rule.
- **The binding.** `preview_sha256` is a SHA-256 over the change asked for (op, owner, group or mode, `recursive`), this policy's SHA-256, and every entry in walk order: its path, type, device, inode, mount id, birth time (where the filesystem reports one), owner, group and mode. Size and change time are not in it, so a file being written stays approvable. On a filesystem without birth times, an entry deleted and created again with the same inode number, owner and mode hashes the same; the chain rule leaves only root able to do that.
- **The change.** The operation walks again and refuses with `exists`, changing nothing, unless the hash is the one given. It then changes each entry that needs it (an entry already as asked is skipped), children before their directory and the target last, each on a descriptor opened by its single-component name from its parent's handle with `O_NOFOLLOW`: that descriptor's `statx` must show the object the walk saw (device, inode, type, mount id, birth time) with the same owner, group and mode, and its link count is checked on it; then `fchown` or `fchmod` acts on it, and `statx` on it reads the change back (`verify_failed` on a mismatch, never a success). A newcomer is never changed, since no directory is read again; an entry replaced, changed or removed stops the operation with `exists`, "N of M entries were changed and K were not". There is no rollback: the audit line (§8) records every entry changed with its old values. A link made after an entry's check is equivalent to one made after its change.
- **Not backed up.** Metadata is not backed up (handoff Q8); the audit line is the record.

**Delete.** The gate's delete (POLICY §3), through the same code, with what root needs on top (handoff D10).
- **The walk and the refusals** are the gate's: each directory opened as an `os.Root` from its parent's handle and re-checked by requested and real path and by `statx` identity, no symlink followed, no other mount entered. Refused, and the preview requests no approval: a root of this policy and a tree holding one; anything outside the write roots, denied or protected; a final symlink; a mount point, the root of another filesystem, and a tree holding one; a character or block device node and a tree holding one (the core unit has `PrivateDevices=yes`); a name starting with `.shell-mcp-delete-` and a tree holding one (an entry an earlier delete left set aside); a non-empty directory without `recursive` (`bad_request`); more than `limits.max_delete_entries` entries (`too_large`). Symlinks inside a tree are removed as links, never followed (only with backups off: below).
- **The binding.** `preview_sha256` is the gate's hash (every entry's path, type, size, device, inode, change time and, where reported, birth time) over its own domain and this policy's SHA-256, so an edit of either the tree or this policy between the preview and the delete is `exists`, and nothing is backed up or deleted.
- **The backup, from the plan.** With `backups.keep` above 0, the delete backs up exactly what it will remove before it removes anything, walking the plan, not the directories: each directory re-opened from its parent's handle with the identity the walk saw, each file opened by its name from its parent's handle (`O_NOFOLLOW`) and required to be the object the walk saw, with the same size and change time, and checked again after it was read. A file is backed up as a file; a directory as a tree, whose archive holds exactly the plan's entries, in walk order, with their modes, owners and modification times. Its size is computed from the plan first, so a backup that would exceed 64 MiB or the store's cap (Backups, below) is refused before anything is written. A tree holding a symlink, FIFO or socket, or such a file as the target, cannot be backed up, so it is not deleted while backups are on (`backup_failed`). An entry replaced or changed while it is being backed up is `exists`, and nothing is deleted. The metadata records the request's `expected_preview_sha256` as `preview_sha256`.
- **The deletion** is the gate's: bottom-up, each entry checked under its name (its size and change time too, so a file written after the backup read it stops the delete before it is removed), set aside under `.shell-mcp-delete-<32 hex>` with `RENAME_NOREPLACE`, checked again there and only then unlinked; anything else is put back and the deletion stops with `exists`, "N of M entries were deleted and K were not". An entry that cannot be put back (its name was taken meanwhile) is left under its temporary name, never deleted, named in the refusal and in the audit line (`set_aside`); POLICY §3 says how to recover it.
- **What remains** is POLICY §3's: a process that finds the random name and replaces it between the second check and the unlink (it has write access to that directory, and so could delete the entry itself); an inode number reused within one system call on a filesystem without birth times; and a process that already holds a listed file open for writing and writes through that descriptor after the entry's last check, whose write lands in an inode that is then removed, while the backup holds the content as it read it.
- **Hard links.** An unlink removes one name, never an inode, so a file with other names is deleted by its name under the write root and its other names keep the inode and its content; there is no link-count refusal, as in the gate (maintainer decision, S4c-4). Two names of one inode inside the tree are backed up as two files.
- **No chain rule.** Unlike chown and chmod, a delete does not require root-owned, not group- or world-writable directories from `/` to the entry (maintainer decision, S4c-4). Unlinking or renaming an entry needs write and search permission on its directory (and its ownership or the directory's in a sticky directory), so an account that could move an entry into the tree, or swap entries during the delete, could unlink it itself; the set-aside and identity checks make root remove only the inodes the approver saw, so a delete under an application-owned directory gives that account nothing it did not have. Restoring a backup over, or of, a moved-in file follows "Files another account could have moved in" (below).
- **Backups of a failed delete.** A delete reports a commit at each unlink and when it leaves an entry set aside. It counts every entry it sets aside, puts back, leaves stranded and unlinks, and a refusal is provably unchanged only when that accounting says so: nothing unlinked, nothing stranded, and as many entries put back as were set aside. Only then is the backup it wrote removed again and listed as `backup_ids_discarded`; any other failure keeps it, including one that stopped after setting an entry aside without putting it back (Backups, below).

**Restore.** A restore puts a backup back as root, over whatever is at its path now, with a recorded owner and mode, so it restores only an intact backup, only over what the approver saw, and never in a way that hands another account a file it could not have made itself (handoff D3, Q3, Q12, R-1, N-6).
- **The backup is verified twice.** The preview reads the backup's data (at most 64 MiB) and requires the size and SHA-256 its metadata records; the restore reads it again, requires both again, and writes those very bytes from memory. A mismatch is `verify_failed` ("the backup's data does not match its record"), and nothing is restored; a missing data file, or metadata that does not decode, is `backup_failed`. A tree's archive must also hold exactly the entry count its metadata records, and only safe relative names of directories and regular files (`verify_failed` otherwise).
- **What it sets.** The recorded owner and group, even outside `owners` (Q3), subject to the moved-in rule below; the recorded mode without setuid, setgid, sticky and world-write, masked by `modes.max` (§4). The preview and the result report both modes: `backup.mode` and `restore.mode` in the preview, `recorded_mode` and `mode` in the result, for a file or a tree's root directory; for a tree, `first` lists the first 50 entries in archive order with their `recorded_mode` and `mode`, `narrowed` counts every entry (the root included) whose mode the mask narrowed, and `truncated` says the list is cut (R-1, P-10).
- **The binding.** `preview_sha256` is a SHA-256 over its own domain, this policy's SHA-256, the backup's id, kind, path, size, SHA-256, entry count and recorded owner, group and mode, the owner, group and mode that will be set, the current state at the path (absent, or a regular file's size, mode, owner, group and SHA-256) and whether the current version will be backed up. `priv_restore_backup` recomputes it, through the same code and refusals, and refuses with `exists`, restoring nothing, unless it equals `expected_preview_sha256`.
- **A file** is then written as `priv_write_file` writes: over the file the preview saw, bound by that file's SHA-256 as `expected_sha256` and committed as a verified replace (a file changed after the recompute is `exists`, and kept), or, when the preview saw none, create-only (`expect_absent`), so a file that appeared is never replaced. Its current version is backed up first, within the store's cap, and that backup records the current content hash as `preview_sha256`; the result's `backup_ids` names it, so a restore can itself be undone by restoring that backup.
- **A tree** is restored only where nothing exists: its root and every directory with an exclusive `mkdir`, every file create-only (`expect_absent`), in archive order (parents first), each with its recorded owner and its masked mode. An entry that appeared meanwhile stops the restore with `exists`, "N of M entries were restored and K were not", leaving what it created and the newcomer untouched; preview again, or delete the partial tree, and restore again. Every entry's path must pass the deny list and the protected set, and a tree may hold at most `limits.max_delete_entries` entries (`too_large`).
- **Retention.** The backup being restored is never pruned by the retention of the backup the restore writes, and the store's cap does not count it as freed (handoff Q12, X-8).
- **Refused at the preview, so no approval is requested:** an unknown id or backups disabled (`not_found`); a path no longer under a write root, denied or protected (`path_denied`); a file restore over a symlink (`path_denied`), a directory (`is_a_directory`), another non-file (`bad_request`), or a file with setuid, setgid, sticky or world-write bits (`policy_denied`); a tree restore where anything exists (`exists`); a backup that does not match its record (`verify_failed`); a current version whose backup would exceed 64 MiB or the store's cap (`backup_failed`); and what the moved-in rule refuses (`path_denied`).

**Files another account could have moved in** (handoff N-6, N-7; maintainer decision, S4c-5). Reading a file as root, or giving a file root wrote another account's ownership, must not hand an account what it could not have got itself. An account that can write a directory on a file's path can move a file from elsewhere on the same filesystem into it (rename and link both need write access to the directory that receives the name), or swap a sibling directory into the path (a rename within one parent needs write access to that parent only, not to the directory moved), have root act, and move the result out again.
- **The chain.** Every directory from the privileged root the path is resolved under (the longest matching read or write root, inclusive) down to the file's parent, each opened from the previous one's descriptor with `O_PATH|O_NOFOLLOW` and checked by `statx`, never by a separate lookup of a path; the last must be the parent the operation holds. A directory is *closed* when it is root's and neither group- nor world-writable (the group bits are the ACL mask, an upper bound on every named ACL entry). Directories above the root are not checked per request: an open one there lets another account replace the root itself, and `check-policy` prints a WARN for each read and write root whose own path has one. Chown and chmod keep their stricter chain from `/` ("Chown and chmod", above).
- **Owner-matched.** A file is *owner-matched* when every directory in its chain is closed, or is owned by the file's owner and is neither group- nor world-writable: then the only account other than root that could have put the file there is its owner, which could read it, or write a file of its own with the same content, anyway.
- **Reads.** `priv_read_file` (the content, and a binary file's SHA-256) and `priv_copy`'s read of its source return a file only when it is owner-matched or world-readable; otherwise they refuse with `path_denied`, naming the first directory that fails, and read nothing. The restore preview hashes a current file under the same rule. `priv_stat`, `priv_list_dir` and `priv_list_backups` return metadata only and are unchanged. Consequence: a group-writable read root, such as a `/var/log` that is `root:syslog 0775` (Ubuntu with rsyslog), refuses every file directly under it that is not world-readable; point read roots at closed subdirectories (for example `/var/log/example-app`) and read system logs with the journal tool.
- **Overwrites.** A write or a copy over an existing file keeps that file's owner and group only when the file is owner-matched (a closed chain included). Otherwise a write needs both `owner` and `group`, from `owners`, and a copy, which has no owner inputs, is refused; both refusals are `path_denied` naming the directory, made before anything is backed up or written. A restore applies the same test to the owner it would set (the recorded one), for a file whether or not one exists there now, and for every entry of a tree, whose own restored directories, with their recorded owners and the modes they will get, extend the chain; otherwise it is refused. A move keeps its inode, owner and mode, and is unchanged.
- **Through the tools.** The composed previews of write, copy and move hash an existing destination through `priv_read_file`, so an overwrite of a file the read rule refuses is refused at its preview, and no approval is requested, even with an explicit owner. One the read rule allows (world-readable) but whose owner and group may not be inherited is refused by the operation after approval, changing nothing, unless both are given.
- **What remains.** An operation that replaces or removes a moved-in file backs it up first, as root, and records its SHA-256 in the backup's metadata, which `priv_list_backups` shows: a delete (which has no chain rule, "Delete" above), a move over it, and a write over it with an explicit owner and group (whose result also carries it as `old_sha256`). The previews of the write, copy and move tools refuse to hash such a file, so for those only a caller that does not go through the tools (a compromised server) gets that far; a delete through `shell_priv_delete_path` does back it up (its preview lists entries, it hashes none). A restore of such a backup is refused by the rule above unless its recorded owner is owner-matched. A new file created as root without an owner is root's (N-3) in any directory, so an account that can write that directory can move it elsewhere with its approved content (handoff N-8, a follow-up). Directories above a root, as said. `priv_exec`'s `{path:read}` placeholders resolve paths for the command, which reads with its own rules (S4c-6).

**Write-class results** carry `backup_ids`, the backups written first; owners and groups are names from `owners`; modes are octal strings within `modes.max`, and a reported `mode` is the mode set (after the mask). `priv_write_file`, `priv_copy` and `priv_mkdir` results also carry `uid` and `gid`, the new inode's owner and group read from its own descriptor after they were set, and `owner` and `group`, their names when they are on the `owners` lists (handoff P-12, added to protocol v1 in place before any release). `priv_exec` has no stdin in v1 (the privileged policy declares no stdin limit).

## 7. Self-checks (fail closed)

The helper refuses to serve when: stdin is not a connected Unix stream socket; the unit's `SHELL_MCP_PRIVD_CLIENT_UID` is missing or not a uid in 1..4294967294; the peer UID is not that value; it is not uid 0; `NoNewPrivs` is not 1; it was built with cgo, or its binary is not root-owned or is group/other-writable; the policy is missing, unreadable, not root-owned or group/other-writable; the policy fails parsing or validation; the policy SHA-256 differs from `SHELL_MCP_PRIVD_POLICY_SHA256`; the policy's `client_uid` differs from `SHELL_MCP_PRIVD_CLIENT_UID`; the unit's `SHELL_MCP_PRIVD_UNIT` is not `core` or `broad`, or is `broad` for a policy that uses no broad unit; its capability bounding set is broader than its unit declares (the core unit's computed set; for the broad unit, root's full set without what its directives drop, §5.2); Landlock is unavailable and the policy does not set `sandbox.landlock: best-effort` (core unit only: the broad unit has no Landlock sandbox).

The checks run in that order, in four steps. **No byte is read from the connection until all of them have passed.**

1. **Authenticate the peer**, from the connection and the unit's environment alone: the socket checks (`fstat`, `getsockopt`, `getpeername`), the unit's client uid, and `SO_PEERCRED`. Nothing is read from disk. A failure closes the connection **without writing a byte** (the gate reports `helper_refused`) and logs one WARN line naming the check (`stdin`, `unit_client_uid` or `peer_uid`) with outcome `refused`. Nothing is ever written to an unauthenticated peer, and it learns nothing about the installation: whatever else is broken, it gets the same silent close.
2. **Every other self-check**, for the authenticated peer. A failure is answered with one response — no id, since the request is unread, and a one-line message that names the failed check and at most a policy field name (never a local path, a value from the root-only policy or a parser's message) — and logged at WARN with the check and the code as the outcome:

   | Check (journal) | Code |
   |---|---|
   | `uid`, `no_new_privs`, `binary`, `policy_file`, `unit` | `helper_install_insecure` |
   | `policy` (parse or validation) | `helper_policy_invalid` |
   | `policy_hash` | `helper_policy_mismatch` |
   | `client_uid` | `helper_client_uid_mismatch` |
   | `capabilities` | `helper_capabilities_broad` |

   The gate passes these codes through unchanged (ARCHITECTURE §4.2).
3. **Landlock** (core unit): a refusal is `helper_sandbox_unavailable` — not the gate's own `sandbox_unavailable`, so the operator can tell which component lacks the sandbox — answered without an id, logged at WARN with the check `landlock`, and the instance exits 1 like the other answered self-check failures.
4. **Only then read the request.** Every outcome from here on is a response carrying the request's id. A request without a valid `ceiling` is `bad_request` as it is decoded. The first check on a decoded request is its unit: an operation meant for the other unit is refused with `helper_wrong_unit` (for `priv_exec`, once the command is known to be declared), before its tier or anything else. The tier, against min(`max_tier`, `ceiling`), comes next (§6).

## 8. Audit

One journald line per connection from the helper unit (stderr, `SyslogIdentifier=shell-mcp-privd`), as one JSON object: the request id, the request's tier `ceiling` (empty on a refused connection, whose request was never read), peer UID and PID, op, sanitized arguments (paths, owners, modes, command id and argument count, backup id, flags — never content, command arguments or output), the backup ids written, outcome and duration. When a failed operation's backups were removed again because it was provably unchanged (§6, Backups), the line lists them as `backup_ids_discarded` (and not in `backup_ids`), so the journal shows they were written and removed. For `priv_chmod` and `priv_chown` the line also carries `changed`: each entry changed, with its mode, owner and group before the change (`path`, `old_mode`, `old_uid`, `old_gid`), also when its read-back then failed, and `changed_total`, how many were changed. The list is bounded at 100 entries or 32 KiB, whichever comes first; `changed_truncated: true` says it was cut. Metadata is not backed up, so this line is the record of the old values. For `priv_delete` the line carries `removed`, the entries removed (logical paths, also when the delete stopped part-way), and `removed_total`, within the same bounds, with `removed_truncated: true` when it was cut; and `set_aside`, the temporary path of an entry the delete set aside and could not put back, when there is one. The args carry `recursive`, never `expected_preview_sha256`. For `priv_restore_backup` the args carry the backup's id as `backup_id` (never `expected_preview_sha256`), and `backup_ids` the backup of the current version it wrote first. The gate principal is not forwarded (the request reaches the helper unchanged); the gate's own audit line for the same request id carries it, so the two lines join on the id (a lowercase UUID v4, validated by both). Priorities: info on success, notice on a refused operation, WARN on a refused connection (a failed self-check or peer check, with the check's name; the outcome is `refused` when the connection was closed without a byte, else the code it was answered with, §7). Everything the broad unit serves logs at WARN (it is root-equivalent); the line carries the package names (identifiers from the allow-lists, never output), the power action and the `unit` label.
