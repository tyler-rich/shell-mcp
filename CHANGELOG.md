# Changelog

All notable changes to shell-mcp. Versions follow [Semantic Versioning](https://semver.org); a release is the tag `vX.Y.Z` on `main`. The design record behind each change is `docs/ARCHIVE.md` §14.

## [Unreleased]

**Added**

- **A memory limit for every child of the gate and the helper** (handoff N-30, N-25's memory half; PR #61): `limits.max_memory_mb` in the gate policy and in the privileged policy (default 1024 MiB, 128 to 16384, never unlimited), applied as `RLIMIT_DATA`, soft and hard, to every command, git, systemctl and journalctl process before its first instruction. The helper's generated units set `MemoryMax=` to the key plus 256M, with `MemorySwapMax=0` and `OOMPolicy=continue`, so a command that reaches the cgroup's limit is killed and the helper still answers. git's thread counts are pinned (`pack.threads=4`, `index.threads=1`, `checkout.workers=1` and the others in `gitx`), so a git operation's memory need does not follow the host's CPU count. `check-policy` reports the limit and warns when the kernel's `ignore_rlimit_data` is set. POLICY §4a, PRIVILEGED §5.
- **`{path:read:fd}`** (handoff N-22): an opt-in placeholder for gate commands that passes the file as the gate's open descriptor (`/dev/fd/4` and up) instead of a path, so a command that reads its argument reads the file the gate checked, whatever happens to its name afterwards. It closes the owner-matched `{path:read}` redirect for such commands. Regular files only, at most 8 per template; the privileged policy refuses it. `exec_preview`, `exec`, `shell_run_read_command` and `shell_run_command` report the descriptors (`fds`), and an approved command is bound to the file's identity. `check-policy` warns about programs measured to give wrong results with a descriptor (`stat`, `du`, `file`, `ls` and `find` without following links; `cp -a`/`-P`/`-r`; `tar` adding a member; `findmnt`; `nginx`; `docker compose`) and checks `/dev/fd`. POLICY §4.
- **Rotating a private-key file as root under approval** (handoff N-5, the private-key half): a new read-tier helper op, `priv_hash_file`, returns a file's size, SHA-256, line count and whether it holds a private key, never its content. The `shell_priv_write_file`, `shell_priv_copy_path` and `shell_priv_move_path` previews hash an existing destination through it, so a key file, or a certificate bundle with its key, can be replaced under an approval that binds the old and new keys' hashes without showing either. `shell_priv_read_file` still refuses the key. The old key is backed up root-only like any replaced file and can be restored; PRIVILEGED §6 says how to remove its backups after a rotation for compromise, and recommends generating keys on the host with a fixed command template: a key written through the tools came from the MCP client and so passed through the model and its provider. The gate's own twin, and the 256 MiB hashing cap, are deferred.
- **Replacing a private key through the gate's own tools under approval** (handoff N-5, the gate's half; S7-3): a new read-tier gate op, `hash_file`, returns a file's size, SHA-256, line count and whether it holds a private key, never its content, under `read_file`'s path rules. With `operator` in `SHELL_MCP_APPROVAL_TIERS`, the previews of `shell_write_file`, `shell_copy_path` and `shell_move_path` hash an existing destination with it instead of reading it, so a key file or a certificate bundle with its key can be overwritten under an approval that binds its hash; the write preview gains `new.private_key` and every one of these previews gains `private_key` for an existing file. TOOLS.md shows how to generate a key on the host with a gate command and move it into place. Added to protocol version 2 in place.
- **Recovering an unfinished dpkg database through the tools** (handoff N-14, S7-4): `shell_priv_recover_packages` and the helper's `priv_pkg_recover_preview` and `priv_pkg_recover` finish what an interrupted dpkg left unfinished, running `dpkg --force-confold --configure --pending` as root in the broad unit under the package operations' protections. The approval binds the unfinished packages (read from dpkg's status with its journal folded in) by hash, and any change before the run is refused. The recovery holds the package operation record and follows the lock rule. At a hang-up or the deadline it answers early and lets dpkg finish; dpkg gets no SIGINT, since it has no graceful stop, and is killed only at `limits.max_timeout_s`. The result comes from dpkg's state alone. With nothing unfinished the tool answers at once, with no approval and nothing run. It needs `packages.allow_recover: true` in the privileged policy (new key, default false), shown in `priv_policy`. Added to protocol version 2 in place. A package that needs a reinstall, or whose dependency is missing, is not recovered: it is named, and left to an administrator (N-36).

- **An offline exposure check of the helper's units** (handoff N-28): `scripts/exposure/run.sh`, in `scripts/ci-local.sh` and a new `exposure` CI job, generates the core unit of the example privileged policy and of every end-to-end policy and rates it with `systemd-analyze security --offline` in the systemd of Debian 13 (257), Ubuntu 24.04 (255) and Ubuntu 26.04 (259), images pinned by digest, failing above the score recorded in `scripts/exposure/scores.txt`. It is shown failing on a unit with `ProtectHome=yes` undone.

**Fixed**

- **The helper's reap of a command's leftover processes** (PR #61): it lists a command's children with the real error when a listing fails (it hid it before), retries within its bound and falls back to scanning `/proc` by parent pid, and still answers `outcome_unknown` unless `wait4` confirms none is left. Listings over `/proc` that swallowed errors no longer give a wrong success: the gate's check that no_new_privs holds on all its threads fails when a thread cannot be read, and the child task count behind `RLIMIT_NPROC` refuses to start a command when `/proc` cannot be counted, rather than dropping the limit.
- **Output redaction pairs a private-key block's labels** (handoff N-34, S7-1): a block now ends at the first `-----END …-----` line of the same label as its BEGIN line, or at the end of the output when there is none, the rule the approval page's masking already used (one finder, `redact.PrivateKeyBlocks`, for both). Before, any END line closed it, so in a malformed block such as `BEGIN RSA … END EC …` the text after the mismatched END was shown. Well-formed keys and all other output are unchanged.
- **The private-key refusal of file reads covers the whole file** (S7-1, found auditing N-34): `read_file`, `priv_read_file` and `priv_hash_file` looked for a key header only in the first 64 KiB, so a key further into a file could be returned by `offset` or `tail_lines` from inside its body, without the header the output redaction needs. They now refuse a file that holds a header anywhere (the whole file up to 256 MiB, in the SHA-256 pass; above that the first 64 KiB, the window and the 1 MiB before it), and `priv_hash_file` reports `private_key` for the whole file. Command, journal and diff output can still show a headerless key body: recorded as N-35 (POLICY §3).
- **A gated `shell_write_file` over a file the gate cannot hash** (above 256 MiB) is refused at its preview with `too_large` (S7-3). Before, its preview had no hash, and the approved write was sent without `expected_sha256` or `expect_absent`: bound to the file's size and mode only. The gate's copy and move already refused this case.
- **The package operations' refusal of an unfinished database names what each package needs** (S7-4): configuring (`dpkg --configure -a`, or the new recovery), a missing dependency installed or the package removed, or a reinstall. Before, every state got "run dpkg --configure -a", which leaves a half-installed or reinstreq package, and one with a missing dependency, as they were. The state is now read with dpkg's journal folded in, as dpkg reads it. The power operations' refusal says the same. The index update is not refused in this state, and never was: `apt-get update` never opens dpkg's database (now documented).
- **A copy's source is searched whole for a private key** (S7-3): the gate's `copy` and the helper's `priv_copy` looked only at the first 64 KiB of the source (up to `max_read_bytes`), so a key past them was copied (never returned to the client). They now refuse it, as `read_file` does since S7-1.

**Changed**

- **The core unit hides `/home`, `/root` and `/run/user` (`ProtectHome=yes`) where no root, command or policy file is under them** (handoff N-28); otherwise `read-only`, as before. The e2e-host exposure threshold is 1.3.
- **Protocol version 2** (ARCHITECTURE §4.0). A server, gate or helper of another version refuses with `protocol_mismatch`, naming both versions and which side to upgrade; a 0.1.0 server or gate gets that message in its own version's frame. A refusal of the version is never reported as `outcome_unknown`. The session hello is unchanged.
- **Privileged `#!` scripts need an acknowledge** (handoff N-26): a command in the privileged policy whose program is a `#!` script (found by its content, so a symlink or a renamed copy counts) is refused at load unless it carries a non-empty `acknowledge`, the existing key. The refusal names the script and its interpreter; an interpreter on the never list is still refused, acknowledged or not. `check-policy` prints `REVIEW script` and the acknowledge on the command's line, and `priv_policy` reports a `script` finding. The gate is unchanged: its scripts run as the service account inside its sandbox, and keep the WARN.
- **The GTFOBins warning checks a script's interpreter** (handoff N-31): in the gate's and the helper's `check-policy`, a `#!` script run by a listed program (`make`, `sed`, …) gets the warning naming both, by the name the `#!` line writes and the name it resolves to, on every step of the script chain.
- **The GTFOBins warning matches by binary identity** (handoff N-33): in the gate's and the helper's `check-policy`, a program or a script's interpreter that is the same file as a GTFOBins-listed binary under the system binary directories (a hard link or a renamed copy of `sed`, `make`, …) gets the warning, which now names the listed program and how it matched (written name, resolved name or binary identity). It is a warning only: it never refuses a policy, and a listed binary that cannot be compared is skipped with a WARN. Policy loads cost about 2% more with 250 commands (POLICY §6).
- **The approval page never shows a private key**: in an argument or preview value (for example the content of `shell_write_file` or `shell_priv_write_file`), each PEM private-key block, from its BEGIN line through the END line of the same label, is shown as `private key, not shown: <bytes> bytes, sha256 <hex>`, and the text around it as it is, so a key cannot hide the rest of a file from the approver. A BEGIN line without its END line is masked to the end of the value. The approval still binds the real value. Before, the page showed up to 4096 bytes of it, enough for a whole key. The two write tools' descriptions now say that content passes through the client and its model provider, and to generate private keys on the host.
- **The order of the version check is a stated requirement** (ARCHITECTURE §4.0): every peer checks the version of a request or response before any other action on it, which is what makes "a version mismatch means nothing ran" true. New tests in the gate and the helper hold it.

**Upgrade notes**

- **Approvals pending across the upgrade of the server fail closed** for `shell_write_file`, `shell_copy_path` and `shell_move_path` over an existing file: the preview gains `private_key` (and a write's `new.private_key`), so the re-call's fresh preview no longer matches (`approval_invalid`); request a new approval. A server of this release needs a gate of this release for those previews (an older 0.2.0 development gate answers `unknown_op` for `hash_file`, and no approval is requested).
- **The core unit now has `ProtectHome=yes`** when nothing the instance sees lies under `/home`, `/root` or `/run/user` (`systemd-analyze security` 1.3 instead of 1.4); with a read or write root, a command or the policy file there it stays `read-only`. `check-policy` says which. Regenerate the units (next note).
- **Upgrade the server, the gate and the helper together.** A 0.1.0 server and a gate of this release, or the reverse, refuse each other with `protocol_mismatch` (the message says which to upgrade); so do a gate and a helper of different releases.
- **Regenerate the helper's units after upgrading** (`shell-mcp-privd units --policy /etc/shell-mcp/privileged.yaml --out /etc/systemd/system`, then `systemctl daemon-reload`): the new units carry `MemoryMax=`, `MemorySwapMax=0` and `OOMPolicy=continue` derived from `limits.max_memory_mb`. A gate or privileged policy that sets `limits.max_memory_mb` is refused by a 0.1.0 gate or helper (unknown key). Commands that need more than 1024 MiB of data (for example `jq` on very large files) need the key raised.
- A gate policy that uses `{path:read:fd}` is refused by a 0.1.0 gate (unknown placeholder).
- A privileged policy that sets `packages.allow_recover` is refused by a helper from before it (unknown key). A policy that declared the documented `dpkg --configure -a` command template as its recovery can keep it (with its acknowledge), but `shell_priv_recover_packages` is the bound alternative (PRIVILEGED §6).
- **A privileged policy with a `#!` script and no `acknowledge` on its command refuses to load** (the helper will not start on it, and `check-policy` says which command). Add a one-line `acknowledge` to each such command after reviewing the script; check the policy first with `shell-mcp-privd check-policy --policy /etc/shell-mcp/privileged.yaml`.

## [0.1.0]

The first release: an MCP server that gives AI clients bounded, audited read and write access to Linux hosts over SSH, without a shell.

**What it contains**

- **Three binaries**, static, for linux/amd64 and linux/arm64: `shell-mcp` (the MCP server, also shipped as a distroless, non-root container image), `shell-mcp-gate` (the SSH forced command on each target) and `shell-mcp-privd` (the optional privileged helper for root actions).
- **The server.** Streamable HTTP with a bearer token (MCP 2026-07-28 and 2025-11-25), or stdio. Host and Origin allow-lists, per-client rate limits and an auth-failure lockout, trusted proxies by address. Pinned SSH host keys only, Ed25519 client keys, no agent, forwarding or PTY. Three profiles: `read-only` (19 tools, the default), `operator` (27) and `admin` (50). `shell-mcp check` verifies every target; `shell-mcp tools` prints the catalogue with schema hashes.
- **The gate.** One request per SSH session, checked against a root-owned policy on the target: read and write roots, a built-in deny list and protected set, exact unit and verb lists, pinned git repositories, and declared commands as exact argv templates with typed placeholders. Before it reads a request it sets `no_new_privs` and a Landlock sandbox computed from the policy, inherited by everything it runs. Shells, interpreters, wrappers, pagers, editors and privilege changers are refused under any name, including through hard links, renamed copies, multi-call binaries and `#!` interpreters. Writes are atomic and read back; deletes and git discards remove exactly what their preview listed, or stop. Service control is authorized by a generated polkit rule. `check-policy` reports what the gate would refuse before it is asked.
- **The privileged helper.** Root actions without sudo, setuid or a root shell: a socket-activated process per request that authenticates the gate's account by kernel peer credentials, applies its own root-owned policy, and runs in a systemd sandbox generated from that policy and pinned to its hash. File operations as root with backups and restore, chown and chmod, declared root commands, apt package operations bound to an approved transaction of exact versions, and a delayed, cancellable reboot or power-off through logind.
- **Human approval.** Destructive operations and every privileged change need a person's approval on the server's own approval page, with a TOTP code from an enrolled approver's authenticator, bound to the exact operation, its preview and both policies, single-use and short-lived. The model cannot approve. Approvals are off by default (gated tools refuse), and a logged `confirm-argument` opt-out exists for those who accept the model approving.
- **Supply chain.** Every file in a signed `SHA256SUMS`; cosign keyless signatures, SLSA build provenance and CycloneDX SBOM attestations for the binaries and the image, all bound to the release workflow at the release tag. Every dependency, image and tool at its newest stable release, enforced in CI.
- **Documentation.** `docs/TARGET-SETUP.md` (target hosts), `docs/CLIENTS.md` (clients, profiles, approvals), the normative design documents, example policies and a hardened reference deployment.

**Known limitations**

- Targets must be Linux with systemd and a kernel with Landlock ABI 4 or newer (Linux 6.7+); tested on Debian 13, Ubuntu 24.04 and Ubuntu 26.04. The helper's sandbox is exercised end to end on Ubuntu 26.04 only.
- Package operations use apt only. Git LFS repositories, repositories on case-folding filesystems, and git repositories that an account other than root or the service account owns or can write are not supported by the git tools; submodules are never entered.
- Deletes and moves are refused on filesystems without `RENAME_NOREPLACE` (for example NFS), and verified replaces on those without `RENAME_EXCHANGE`.
- UDP is not restricted by the gate's sandbox (the target kernels cannot govern it).
- Approvals live in memory and are lost when the server restarts. MCP elicitation is not used for approval; clients relay the approval page's URL instead.
- OAuth is not supported: keep the server on a LAN or VPN, behind a TLS-terminating proxy, never on the public internet.
- One profile per server instance; run several instances for several ceilings.

**Open items after this release**

- **N-5:** an approved copy or move over an existing file cannot be approved when that file is larger than 256 MiB or starts with a private key, because the preview hashes it through the read operation. Workaround: delete the destination first (its own approval), then copy or move without overwriting.
- **N-22:** a declared command's `{path:read}` is passed as a path, not as the descriptor the gate checked, so an application account that owns a directory on that path can redirect what the command reads to another file the service account can read. Planned as an opt-in per template.
- **N-25:** an account that can write a git submodule's directory in a listed repository can make git status, diff, pull and discard wait until their timeout (a FIFO in the submodule's git files). Nothing runs; the request times out.
- **N-26:** a declared command that is a `#!` script is judged by its interpreter; what the script itself runs is not inspected. Review every script you declare, above all in the privileged policy.
